### Fixed
- **Real performance problem, found and fixed via real-machine testing, not assumed**: `WindowsBinaryDiscoveryScanner`'s first real-machine run took 6m39s and produced 29,461 binaries, because several COM registrations (of the ~14,189 found in Phase 4B) resolve into `%windir%\System32`/`SysWOW64`, and fully walking those directories made per-root bounds insufficient in aggregate. Fixed with `SystemDirectoryExclusion` (skip full walks under `%windir%`, still check specifically-referenced files directly) — re-measured at 8.3 seconds, 18,125 binaries, a >45x speedup with no loss of application-relevant coverage.

## Unreleased (Phase 5A)

### Added
- New project `ServerSleuth.Analysis` (plain `net8.0`, references `ServerSleuth.Core` only): the dependency correlation foundation. `CorrelationEngine` orchestrates 10 `ICorrelationRule`s over already-discovered entities — Site→HOSTS→Application, Application→USES→ApplicationPool, Application→CONFIGURES→Configuration, Application→CONTAINS→Binary, Service→RUNS→Binary, ScheduledTask→RUNS→Binary, COM→REFERENCES→Binary, IISBinding→BINDS_TO→Certificate, Binary→IMPORTS→Binary (same-directory-only resolution), Configuration→REFERENCES→Runtime — producing an evidence-backed `DependencyGraph` (Core, Phase 1, unchanged) with full rejection diagnostics for every candidate that didn't become an edge.
- `WindowsPathNormalizer` — the single reusable Windows path normalizer (case-fold, trailing-separator trim, quoted-path unwrap, `/`→`\`, safely-resolvable `%ENVVAR%` expansion via injectable `IEnvironmentVariableResolver`); never collapses `Program Files`/`Program Files (x86)`, never merges distinct UNC hosts.
- `CommandLineReference` — parses raw command-line-shaped strings (e.g. Service `ImagePath`) into executable path + arguments using the same never-guess-on-ambiguity algorithm as Phase 4B's `ServerReference`, reimplemented (not referenced) to keep this layer platform-agnostic.
- `Core.Enums.DependencyEdgeType` extended with `Contains`, `Imports`, `Configures`.
- 67 new tests: path normalizer, command-line parser, correlation context/identity resolution, correlation engine (rejection/merge/determinism), one test class per rule, a full synthetic "ERP" server fixture (skill.md §22) exercising all 9 relationship kinds end-to-end, and a negative fixture (skill.md §23: same-filename-different-app, same-display-name-different-identity, orphaned COM registration).
- `SCANNERS.md`/`ARCHITECTURE.md` extended with the full correlation architecture, identity resolution rules, rule table, and known limitations.

### Known Limitations
- Configuration's Database/Endpoint/UNC references are not correlated into graph edges yet — no scanner produces those entity types; they remain visible as `Configuration` metadata only.

## Unreleased (Phase 5B)

### Added
- `Core.Boundaries.ApplicationBoundary` (Core) — a new model for "which discovered entities appear to belong to the same logical workload," deliberately distinct from `Core.Models.Application` (which remains IIS-site-scoped, unchanged since Phase 4A).
- `ServerSleuth.Analysis/Correlation/Boundaries/`: `ApplicationBoundaryEngine`, `WorkloadAnchor`/`WorkloadAnchorKind`, `BoundaryCandidate`, `BoundaryAnalysisResult`, `BoundaryDiagnostics` — builds workload boundaries anchored on IIS Applications, Windows Services (with a resolvable executable), and Scheduled Tasks (with a resolvable executable); membership comes from Phase 5A's existing `Contains`/`Configures`/`Runs` edges plus a direct (not rediscovered) read of `Configuration.Metadata["OwnerEntityId"]`.
- Cross-workload merge rule: exactly two anchors sharing an identical RUNS target merge into one boundary at High confidence; three or more sharers are treated as common/shared infrastructure and are never merged (recorded as a diagnostic instead).
- Common-parent-directory pairs are recorded as ambiguous-candidate diagnostics, never merged; name similarity is not implemented as merge evidence at all.
- 13 new tests: `ApplicationBoundaryEngineTests` (10) and `NegativeBoundaryFixtureTests` (3 — the two required negative fixtures from skill.md §24, plus an independent-merges-don't-interfere case).
- `ARCHITECTURE.md`/`PROGRESS.md` extended with the full Application Boundary architecture, membership/merge rules, and known limitations. `SCANNERS.md` unchanged — no scanner contract was affected.

### Known Limitations
- No explicit-merge-evidence sources (config referencing another executable, shared database identifier, application manifest) are implemented — only the two rules Phase 5B's instructions specified (Contains/Configures/Runs membership, and exactly-2-sharer RUNS-target merging).
- Certificates and COM registrations are not yet assigned to any boundary — no rule in this phase's scope connects them to a specific Application/Service/Task anchor.

## Unreleased (Phase 5D)

### Added
- `ServerSleuth.Analysis/Correlation/Validation/`: `GraphValidator` — a pure, read-only diagnostic layer over Phase 5A/5B/5C's output. Implements 12 validation categories (Node/Edge Integrity, Duplicate Detection, Evidence Completeness/Validity, Provenance Integrity, Confidence Consistency/Escalation, Self-Edge Detection, Cycle Detection, Orphan Analysis, Unresolved Dependency Analysis, and domain-specific ExternalDependency/Certificate/COM/Runtime checks), producing `GraphValidationResult { Findings, Orphans, Cycles, Summary }`.
- Cycle detection via an iterative (non-recursive) Tarjan's strongly-connected-components algorithm, classifying each cycle Strong (involves Runs/Imports/DependsOn) or Weak (Contains/References only) without ever deleting or rejecting it.
- Orphan classification (Expected/Potential/Unresolved) so isolated COM registrations, unreferenced Runtimes, and unused Certificates are never flagged as errors, while an isolated Service/ScheduledTask/WebSite/Application is.
- 41 new tests in `test/ServerSleuth.Analysis.Tests/Correlation/Validation/`, including a full Phase 5A→5B→5C→5D pipeline run over the ERP fixture, re-validation of every existing negative fixture (200 unrelated COM registrations, shared-parent-directory workloads, 3-way shared executable, same-named DLLs in separate app roots, multiple runtime versions, missing binary), a synthetic 1,000-node/2,000-edge large-graph performance test, and a no-mutation guarantee test.
- `ARCHITECTURE.md`/`PROGRESS.md` extended with the full validation architecture, category-by-category rationale, and known limitations. `SCANNERS.md` unchanged — no scanner contract was touched this phase.

### Known Limitations
- Duplicate-node and duplicate-edge detection cannot be triggered through `DependencyGraph`'s own public API (it structurally prevents both) — both checks exist as regression safety nets per skill.md's own framing, verified to correctly report zero on well-formed graphs.
- Confidence-escalation checking validates against the boundary's own confidence value; it does not attempt to reverse-engineer exactly which single upstream edge a derived dependency came from when several could match.

## Unreleased (Phase 6B)

### Added
- `ServerSleuth.Linux/Packages/`: `linux-package-scanner`, backed by `DpkgPackageProvider`/`RpmPackageProvider`/`ApkPackageProvider` (one `IPackageManagerProvider` per manager, mirroring the Windows `IRuntimeDetector`-per-family pattern). Each manager is queried directly and independently via a fixed, machine-readable format string — never `apt`/`dnf`/`yum`/`zypper`/`apk add|del`. Produces `Core.Models.Package` (Phase 1, unchanged), deduplicated within one manager's own results, never merged across managers.
- `ServerSleuth.Linux/Runtimes/`: `linux-runtime-discovery-scanner` covering .NET Runtime/SDK, Java, Python (multi-interpreter, never merged), Node.js/npm, PHP, and Go — reusing the exact same `IRuntimeDetector`/`RuntimeDetectionRow`/`RuntimeDetectionResult`/`RuntimeEntityKind`/`RuntimeEntityBuilder`/`RuntimeDetectionDefaults` model Windows's Phase 4D detectors use.
- `ServerSleuth.Linux/Cron/`: `linux-scheduled-task-scanner` discovering cron jobs from `/etc/crontab`, `/etc/cron.d/*`, `/etc/cron.{hourly,daily,weekly,monthly}/*` (run-parts), and `/var/spool/cron/crontabs/*` (Debian) or `/var/spool/cron/*` (RHEL fallback) — reusing `Core.Models.ScheduledTask` (Phase 1, unchanged). Commands are redacted through `ISecretRedactor` before storage; executable paths are extracted only when explicit (never guessed via PATH or shell evaluation).
- **Architectural extraction**: `IRuntimeDetector`, `RuntimeDetectionRow`, `RuntimeDetectionResult`, `RuntimeEntityKind`, `RuntimeEntityBuilder`, `RuntimeDetectionDefaults`, and the `dotnet` CLI output-line parser moved from `ServerSleuth.Windows.Runtimes` to `ServerSleuth.Infrastructure.Runtimes`, so Linux's runtime detectors reuse them instead of duplicating ~150 lines of entity-mapping/confidence logic. `RuntimeEntityBuilder.Build` gained an optional `resolveSource` parameter so each platform supplies its own Source label; Windows's call site was updated to preserve its exact prior behavior — verified by the full pre-existing 299-test Windows suite passing unmodified.
- `AddServerSleuthLinux()` extended with the three package providers, `IExecutableLocator`→`LinuxExecutableLocator`, the seven runtime detectors, and the two new scanners.
- 65 new tests in `test/ServerSleuth.Linux.Tests/`, all fixture/fake-based.
- `ARCHITECTURE.md`/`IMPLEMENTATION_PLAN.md`/`SCANNERS.md`/`PROGRESS.md` extended with the full package/runtime/cron architecture and known limitations.

### Fixed
- **Real, host-specific bug found via test failure, not assumed**: `System.IO.Path.GetDirectoryName`/`Path.Combine` silently rewrite `/` to `\` when the assembly runs on Windows, which would corrupt every Linux-shaped path this project manipulates on a non-Linux host. Every Linux runtime detector now uses a small internal `LinuxPath` helper (forward-slash-only) instead.

### Known Limitations
- No explicit-merge-evidence beyond within-manager package deduplication and same-executable-path runtime/cron identity — nothing new invented beyond what this phase's instructions specified.
- `apk`'s Maintainer/Description are not queried (not exposed by `apk info -v` without a second, less reliable command).
- Cron executable-path extraction only recognizes an explicit leading absolute path — a bare command name or shell-chained command stays unresolved rather than guessed.
- No real-machine validation was performed for the two new scanners — the development host is Windows; the smoke test (extended to cover all seven scanners) honestly reports this rather than faking it.

## Unreleased (Phase 6C)

### Added
- `ServerSleuth.Linux/Containers/`: `linux-container-scanner`, backed by `IContainerRuntimeProvider` implementations `DockerContainerRuntimeProvider`/`PodmanContainerRuntimeProvider` (both thin wrappers over a shared internal `ContainerCliRuntimeProvider`, parametrized only by executable name, avoiding duplicated CLI/JSON parsing between the two runtimes). Discovers Containers, Images, Volumes, and Networks via read-only commands only (`ps -aq`, bulk `inspect`, `images --format json`, `volume ls --format json`, `network ls`+`inspect`) — never `exec`/`run`/`start`/`stop`/`rm`/`pull`/`push`/`build`/`commit`, never a shell string.

- `ContainerRuntimeAvailability` (`Supported`/`PartiallySupported`/`NotInstalled`/`AccessDenied`/`Unavailable`) classifies each runtime without ever assuming Docker is usable merely because the `docker` executable exists on PATH.
- Environment variable **names only** are ever recorded (never values); Labels/Entrypoint/Command are passed through `ISecretRedactor` before storage. Container/Image/Volume/Network identity is deterministic and runtime-qualified (e.g. `container:{runtime}:{id}`) so Docker and Podman entities never collide.
- `AddServerSleuthLinux()` extended with the two container runtime providers and the container scanner (now 8 scanners total).
- 36 new tests in `test/ServerSleuth.Linux.Tests/Containers/`, including a dedicated negative-security suite asserting (via `FakeProcessRunner.Invocations`) that no forbidden subcommand or shell executable is ever invoked.
- `ARCHITECTURE.md`/`IMPLEMENTATION_PLAN.md`/`SCANNERS.md`/`PROGRESS.md` extended with the full container discovery architecture, security boundaries, and known limitations. Integration smoke test extended to cover the container scanner alongside the existing seven.

### Known Limitations
- Image `OS`/`Architecture` are not populated — not exposed by `docker images --format json` without a second per-image `inspect` call, judged out of scope for this phase; left `null` rather than guessed.
- `ImageRow.SizeDisplay` preserves Docker's raw human-formatted size string rather than converting to a numeric byte count.
- No `Container → host Process` correlation is performed — deliberately deferred to Phase 5 analysis, and only when explicit namespace evidence exists.
- No real-machine validation was performed for the new scanner — the development host is Windows; the smoke test (extended to cover all eight scanners) honestly reports this rather than faking it.

## Unreleased (Post-GUI-7 fix — real WPF binding crash under InvariantGlobalization)

### Fixed
- **A real, previously-shipped defect**, found only because a user actually ran the published `dist/ServerSleuth.exe`, clicked into the app, and reported the footer error message: with `InvariantGlobalization=true` (`ServerSleuth.Gui.csproj`), WPF's data-binding engine still tries to resolve `FrameworkElement.Language`'s default value ("en-US") to a real, non-invariant `CultureInfo` the first time ANY bound control on ANY page actually attaches to the visual tree and runs a layout pass — throwing `InvalidOperationException: Cannot find non-neutral culture related to 'en-us'`, caught by `App`'s own exception boundary and surfaced only as the generic "unexpected error" footer message. GUI-1's Dashboard placeholder has no real bound controls, so this was never hit until a page with actual form bindings (Scan Configuration) was reached — reproducible with or without the GUI-7 language toggle; unrelated to it.
- Fixed in `App`'s static constructor: `FrameworkElement.LanguageProperty.OverrideMetadata(...)` overrides every `FrameworkElement`'s default `Language` to the one culture that always resolves under invariant globalization, before any window is constructed. The existing `InvariantGlobalization=true` decision was not reversed.
- Also fixed: `CompositionRoot`'s `services.AddLogging()` registered zero providers, so `GuiExceptionHandler`'s "See application logs for details" was never actually true — nothing was ever logged anywhere. New `FileLoggerProvider` (no third-party package) writes to `%LOCALAPPDATA%\ServerSleuth\logs\gui-{date}.log`, lazily (no filesystem write merely from building the composition root, preserving GUI-1's side-effect-free-composition guarantee).

### Added
- `RealWindowNavigationSmokeTests` (`ServerSleuth.Gui.Tests`): constructs a REAL `App`/`MainWindow`/composition root and navigates every page with a real WPF layout pass — catches any genuine binding/converter/layout exception regardless of runtime config. Cannot alone catch the InvariantGlobalization-specific bug above (the VSTest host process doesn't itself set that switch).
- `ServerSleuth.Gui.RealWindowHarness` (new project, `test/`): a small standalone WPF executable that DOES set `InvariantGlobalization=true` (mirroring the real shipped `ServerSleuth.Gui.exe` exactly), run as a real child process. `RealWindowRuntimeConfigTests` asserts on its exit code — this is what actually would have caught the shipped defect, verified by deliberately reverting the fix and confirming both the harness and the wrapper test fail with the real stack trace, then re-confirming both pass with the fix restored.
