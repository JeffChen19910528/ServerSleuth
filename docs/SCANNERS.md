# SCANNERS.md

This document covers every `IDiscoveryScanner` implementation (Phase 3 onward) plus the **Infrastructure Abstractions** they're built on (Phase 2), per skill.md §49's requirement that each piece document Purpose / Supported Platforms / Data Sources / Permissions / Entities Produced / Evidence Produced / Known Limitations / Security Considerations / Tests.

---

# Windows Scanners (Phase 3)

## Windows OS Scanner (`windows-os-scanner`)

- **Purpose**: Identify the current machine and its OS — the root of every other entity's context.
- **Supported Platforms**: Windows.
- **Data Sources**: `Environment`/`RuntimeInformation` (machine name, OS description, architecture, .NET runtime, system directory, execution user); `HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion` (ProductName, EditionID, CurrentBuildNumber, UBR, DisplayVersion/ReleaseId) when readable.
- **Permissions**: No elevation required; registry read only, standard user can read `CurrentVersion`.
- **Entities Produced**: `Server`, `OperatingSystem`.
- **Evidence Produced**: `Command` (Environment/RuntimeInformation calls), `Registry` (`HKLM\...\CurrentVersion`) when the registry read succeeds.
- **Known Limitations**: If the registry read fails, falls back to `RuntimeInformation.OSDescription` at `High` (not `VeryHigh`) confidence rather than failing — this is a deliberate degrade, not a gap. Edition/build number are simply absent (not guessed) when their registry values are missing.
- **Security Considerations**: Read-only registry access; no values here are ever secret-shaped.
- **Tests**: `WindowsOsScannerTests` (pure `BuildEntities` mapping — with/without registry data, metadata capture) + `WindowsScannerIntegrationTests.WindowsOsScanner_DiscoversCurrentMachine` (real machine).

## Windows Process Scanner (`windows-process-scanner`)

- **Purpose**: Enumerate running processes with enough detail (path, command line, parent, owner) to correlate them to services/applications later.
- **Supported Platforms**: Windows.
- **Data Sources**: `System.Diagnostics.Process.GetProcesses()` for PID/name/start time (`ProcessEnumerator`); `Win32_Process` WMI class + its `GetOwner()` method for executable path, command line, parent PID, and owning account (`ProcessWmiProvider`).
- **Permissions**: Runs with calling-process privileges. Many system/protected processes deny `StartTime`, `ExecutablePath`, or `GetOwner()` — this is expected, not an error.
- **Entities Produced**: `Process`.
- **Evidence Produced**: `Process` (PID), `Command` (WMI Win32_Process) when a WMI row was found.
- **Known Limitations**: Per-process architecture (x86/x64) is not determined (`EntityArchitecture.Unknown` on every `Process` entity) — no cross-platform-safe managed API exists for this in .NET 8 without P/Invoke; deferred. `ProcessWmiProvider.GetOwner()` is one WMi call per process, which is a real per-scan cost on a machine with many processes — acceptable for Phase 3's correctness-first priority (skill.md §51), flagged for Phase 10 hardening if it proves too slow on very large servers.
- **Security Considerations**: Never attempts to open a process with elevated access rights beyond what `Process`/WMI request by default; never executes or terminates anything.
- **Tests**: `WindowsProcessScannerTests` (pure `BuildEntity` — full WMI info, missing WMI info, access-denied executable path vs. entirely-unavailable WMI row, start-time access denied) + `WindowsProcessScannerScanAsyncTests` (fake enumerator/WMI provider — Supported/PartiallySupported/empty aggregation) + `WindowsScannerIntegrationTests.WindowsProcessScanner_DiscoversTheCurrentTestProcessItself` (real machine; this test caught and drove the fix for a real bug — see Known Limitations of `ProcessEnumerator` below).

**Sub-note — `ProcessEnumerator` bug fixed during Phase 3**: the integration test above initially failed with an unhandled `System.ComponentModel.Win32Exception` from `Process.StartTime` on an access-denied process — the code only caught `UnauthorizedAccessException`/`InvalidOperationException`. Fixed by also catching `Win32Exception` (`src/ServerSleuth.Windows/Process/ProcessEnumerator.cs`). This is the kind of gap real-machine integration testing exists to catch; fixture-only tests would not have found it since a synthetic `ProcessSnapshot` never exercises the real `Process.StartTime` getter.

## Windows Port Scanner (`windows-port-scanner`, backed by `WindowsPortInspector`)

- **Purpose**: Enumerate listening TCP/UDP endpoints with the owning process, providing the low-level data point (`Port.OwningPid`) that Phase 5's Correlation engine will turn into a `Port → Process` edge.
- **Supported Platforms**: Windows. Implements Phase 2's cross-platform `IPortInspector` contract.
- **Data Sources**: `MSFT_NetTCPConnection` (filtered `State = 2`, i.e. Listening) and `MSFT_NetUDPEndpoint` CIM classes in `root\StandardCimv2` (`NetworkTableProvider`) — chosen over `netstat` text parsing specifically because these classes expose `OwningProcess` directly, matching skill.md §13's "the actual owning process is authoritative." Process name resolved via `Process.GetProcessById` (`ProcessNameResolver`).
- **Permissions**: No elevation required to query these CIM classes as a standard user.
- **Entities Produced**: `Port`.
- **Evidence Produced**: `NetworkSocket`.
- **Known Limitations**: Only *listening* TCP connections are captured (not established/other states) and all UDP endpoints (UDP has no listen/established distinction) — matches the scanner's stated goal ("取得 listening TCP/UDP endpoints"). If a process has already exited between the CIM query and the `ProcessNameResolver` lookup, `ProcessName` is left unset with a `ProcessNameStatus = Unavailable` metadata entry rather than an empty string.
- **Security Considerations**: Read-only WMI query; never uses the port/process data to open connections itself.
- **Tests**: `WindowsPortScannerTests` (pure `BuildEntity` mapping + fake-inspector `ScanAsync` success/failure paths) + `WindowsScannerIntegrationTests.WindowsPortInspector_EnumeratesEndpointsWithoutThrowing` (real machine, 104 endpoints observed during Phase 3 validation).

## Windows Service Scanner (`windows-service-scanner`)

- **Purpose**: The most important Phase 3 scanner — map every Win32 service to its executable, start account, start type, and dependencies, not just name/status.
- **Supported Platforms**: Windows.
- **Data Sources**: `ServiceController.GetServices()` for name/display name/status (`ServiceEnumerator` — this method only returns Win32 services, not device drivers, which matches skill.md §7's scope without extra filtering); `HKLM\SYSTEM\CurrentControlSet\Services\<name>` for `ImagePath`, `ObjectName` (start account), `Start`/`DelayedAutostart` (start type), `DependOnService`, `Description`, and presence of `FailureActions`; `...\Parameters\ServiceDll` for svchost-hosted services (`ServiceRegistryDetailReader`).
- **Permissions**: No elevation required for standard-user reads of these registry keys.
- **Entities Produced**: `Service`.
- **Evidence Produced**: `ServiceConfiguration` (SCM), `Registry` (`HKLM\SYSTEM\CurrentControlSet\Services\<name>`) when the registry read succeeds.
- **Known Limitations**: `FailureActions` (Recovery Configuration) is detected as present/absent (`HasRecoveryConfiguration` metadata flag) but its binary structure is not parsed — skill.md marks this as "if technically feasible," and full binary parsing was judged out of scope for Phase 3's time budget. `Description` is stored as the raw registry string, which for many built-in services is an indirect resource reference (`@%SystemRoot%\...,-123`) rather than resolved text.
- **Security Considerations**: The service account **name** is captured (and tagged `MigrationRelevant` when it's not one of `LocalSystem`/`NT AUTHORITY\LocalService`/`NT AUTHORITY\NetworkService`/`NT AUTHORITY\SYSTEM`) but no password is ever read or could be — Windows does not expose service account passwords via this registry key (they live in the separately-secured LSA secrets store, which this scanner never touches).
- **Tests**: `WindowsServiceScannerTests` (pure `BuildEntity` — full detail, migration-relevant tagging for custom vs. built-in accounts, all start-mode mappings, delayed-autostart labeling, missing-detail partial case, recovery-configuration flag) + `ServiceRegistryDetailReaderTests` (fake registry reader — full read, missing key, access-denied key) + `WindowsScannerIntegrationTests.WindowsServiceScanner_DiscoversRunningWin32Services` (real machine, 325 services observed during Phase 3 validation).

## Windows Installed Software Scanner (`windows-installed-software-scanner`)

- **Purpose**: Enumerate installed software from all three Uninstall registry locations.
- **Supported Platforms**: Windows.
- **Data Sources**: `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall` (`RegistryView.Registry64`), the same path read via `RegistryView.Registry32` (the OS registry redirector transparently maps this to the WOW6432Node view — no hardcoded `\WOW6432Node\` path needed), and `HKCU\SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall`.
- **Permissions**: No elevation required for standard-user reads.
- **Entities Produced**: `Software`.
- **Evidence Produced**: `Registry` (full key path, including which of the three sources).
- **Known Limitations**: **Does not merge entries across the three sources or across duplicate-looking entries** — every registry key becomes its own `Software` entity, with the registry path baked into its Id, specifically so accidental ID collisions are impossible. Real deduplication (deciding two entries are "the same" logical software) is left to Phase 5's Correlation engine, which will have the full identity fields (Name/Publisher/Version/Architecture/InstallLocation) to work with — see the ARCHITECTURE.md decisions log entry for why this was decided at scanner-design time rather than partially implemented here. Entries missing `DisplayName` or with `SystemComponent = 1` are skipped (they represent patches/components, not user-visible software) — this is a documented filter, not silent data loss. Per-user (HKCU) entries get `EntityArchitecture.Unknown` since architecture isn't reliably determinable from that location alone.
- **Security Considerations**: Read-only registry access; `UninstallString` is captured as-is (it is a command line, not a secret, per skill.md's own example schema) — no execution of it ever happens.
- **Tests**: `SoftwareRegistryRowBuilderTests` (pure filter/parse logic — valid entry, missing DisplayName, SystemComponent, unparsable install date, missing optional fields) + `WindowsInstalledSoftwareScannerTests` (pure `BuildEntity` architecture tagging, distinct-ID-across-sources proof + fake-registry-reader `ScanAsync` aggregation/partial/skip behavior) + `WindowsScannerIntegrationTests.WindowsInstalledSoftwareScanner_ReadsUninstallRegistryWithoutThrowing` (real machine, 79 entries observed during Phase 3 validation).

## Windows IIS Scanner (`windows-iis-scanner`, Phase 4A)

- **Purpose**: Discover IIS Sites, their virtual Applications, Application Pools, and bindings — the critical discovery subsystem skill.md §8 calls out.
- **Supported Platforms**: Windows (specifically machines with the IIS Management components installed — see Known Limitations).
- **Data Sources**: `Microsoft.Web.Administration.ServerManager`, loaded from its well-known OS path (`%windir%\System32\inetsrv\Microsoft.Web.Administration.dll`) via `Assembly.LoadFrom` + `dynamic` at **runtime only** (no compile-time reference — see ARCHITECTURE.md's decisions log for why). Reads: `Sites` (Name, Id, State, Bindings), each site's `Applications` (Path, ApplicationPoolName, root `VirtualDirectories` entry's PhysicalPath), and `ApplicationPools` (Name, State, ManagedRuntimeVersion, ManagedPipelineMode, ProcessModel.IdentityType/UserName, Enable32BitAppOnWin64, StartMode).
- **Permissions**: Reading IIS configuration through `ServerManager` requires read access to `applicationHost.config`/`redirection.config` — on this dev machine, a **non-elevated** account was denied access to `redirection.config` (confirmed independently via a plain, non-elevated `Get-IISAppPool` PowerShell call failing identically), and the scanner correctly reported `AccessDenied` rather than crashing or misreporting `NotInstalled`. An elevated account, or one with IIS management permissions, would see `Supported`/`PartiallySupported` instead.
- **Entities Produced**: `WebSite`, `Application` (reused from the generic domain model — see the ARCHITECTURE.md decisions log for why no separate `IisApplication` type exists), `ApplicationPool`.
- **Evidence Produced**: `IisConfiguration` on every Site/Application/ApplicationPool entity.
- **Known Limitations**:
  - Requires `Microsoft.Web.Administration.dll` to exist at its standard path — present when the IIS Management Console/Scripting Tools components are installed alongside the Web Server role; a genuinely minimal IIS install without management components would report `NotInstalled` even though the WWW service exists. This is treated as an acceptable, documented boundary rather than special-cased.
  - Certificate binding detail is thumbprint + store name only (`WebSite.CertificateThumbprint` for the primary binding, `BindingN.CertificateThumbprint`/`BindingN.CertificateStore` metadata for every binding) — never the certificate itself or its private key. Full certificate metadata (subject, issuer, expiry) is Phase 4C's `CertificateScanner`'s job, not this one's.
  - `WebSite`'s singular `Protocol`/`HostName`/`Port` fields (a Phase 1 model shape, not new) reflect only the *first* binding; every binding is still fully represented in `Bindings` (formatted strings) and per-index `Metadata`.
  - Physical-path "inheritance" for sub-applications isn't really a distinct IIS concept (every `Application`'s root virtual directory has its own explicit `PhysicalPath` in `applicationHost.config`) — `IisApplicationRow.PhysicalPathInherited` exists in the DTO for forward-compatibility but is not currently set to `true` by the real provider.
- **Security Considerations**: Never reads `applicationHost.config` as raw text and never dumps full configuration sections into evidence — only the specific typed properties needed for these three entity types are read. `UserName`/account fields on `ApplicationPool` are captured (and tagged `MigrationRelevant` when it's a `SpecificUser` identity, mirroring the Windows Service Scanner's convention) but no password is ever read or accessible through this API.
- **Tests**: `IisScannerBuildEntitiesTests` (pure `BuildEntities` — primary-binding mapping, certificate metadata, root vs. sub-application naming/physical path, `ComponentEntityIds` referencing site+pool, app pool field mapping, `SpecificUser` identity + `MigrationRelevant` tagging, "No Managed Code" runtime label, missing-physical-path handling, stopped-site status mapping, empty snapshot) + `IisScannerScanAsyncTests` (fake provider — NotInstalled/AccessDenied/Failed/Available-with-and-without-partial-failures) + `WindowsScannerIntegrationTests.IisScanner_AgainstRealMachine_NeverThrowsAndReportsAValidStatus` (real machine — accepts any of the four valid outcomes and asserts appropriately per outcome; observed `AccessDenied` on this dev machine's non-elevated execution context, which is itself a correct, validated result).

## Windows COM/ActiveX Scanner (`windows-com-scanner`, Phase 4B)

- **Purpose**: Discover registered COM/ActiveX components — CLSID, ProgID, server path/type, threading model, TypeLib reference — the mandatory COM discovery subsystem skill.md §9 calls for.
- **Supported Platforms**: Windows.
- **Data Sources**: `HKLM\SOFTWARE\Classes\CLSID` (`RegistryView.Registry64`), the same path via `RegistryView.Registry32` (OS registry redirector maps this to `WOW6432Node` transparently — no manual `\WOW6432Node\` path, same convention as the Phase 3 Software scanner), and `HKCU\SOFTWARE\Classes\CLSID`. For each CLSID key: its own default value (friendly name), and — only for child keys actually present (`GetSubKeyNames` checked first) — `InprocServer32` (default value + `ThreadingModel`), `LocalServer32` (default value), `ProgID` (default value), `TypeLib` (default value), `Version` (default value). For a resolved server path that exists on disk: file size, last-write-time (via Phase 2's `IFileSystemReader`), and `FileVersion`/`ProductVersion`/`CompanyName`/`ProductName` (via the new `IFileVersionMetadataReader`, wrapping .NET's standard, non-executing `FileVersionInfo.GetVersionInfo`).
- **Permissions**: No elevation required for standard-user reads of these CLSID keys on this dev machine. Both whole-registry-source denial (all CLSIDs under one of the three roots) and per-CLSID denial (an individual key with restrictive ACLs) are handled distinctly — see Permission Handling below.
- **Entities Produced**: `ComComponent` (existing Phase 1 entity, unchanged).
- **Evidence Produced**: `Registry` — one record per entity, `Location` is the full key path including CLSID, `Detail` states scope+view.
- **Registry View / Scope Handling**: every entity records `Metadata["RegistrationScope"]` (`Machine`/`User`) and `Metadata["RegistryView"]` (`Registry64`/`Registry32`/`Default`). The same CLSID registered in two views/scopes produces **two separate entities** (`Id = com:{scope}:{view}:{CLSID}`), never silently merged — real dedup is Phase 5's job, using the identical `Clsid` field (canonicalized to uppercase) both entities share.
- **Server Path Handling**: `ServerType` metadata is one of `InProcess`/`LocalServer`/`Both`/`Unknown`. A quoted server value (with or without trailing arguments) is parsed unambiguously; an **unquoted value containing a space is never guessed** — it's recorded as `Metadata["{Key}Status"] = "RawReferenceDetected"` with the untouched (but secret-redacted) raw value in `Metadata["{Key}RawValue"]`, per skill.md §16's explicit "don't guess" instruction. `LocalServer32`'s parsed trailing arguments are redacted via the existing `ISecretRedactor` before becoming metadata, with `Metadata["SecretDetected"] = "true"` set if a secret pattern was found in them.
- **File Verification**: a resolved server path that doesn't exist on disk gets `Metadata["ServerPathStatus"] = "NotFound"` (measured on this dev machine: 148 of 14,189 components — real dangling COM registrations, valuable migration-risk evidence); one that can't be read gets `"AccessDenied"`. `Version`/`Publisher` on the entity come from the file's VERSION resource when available, falling back to the registry's own `Version` subkey value.
- **Known Limitations**:
  - **No PE architecture (x86/x64/ARM64) detection** — every `ComComponent.Architecture` is `Unknown`. This is a deliberate Phase 4B scope boundary (skill.md §2 excludes "DLL deep analysis"; custom PE header byte-parsing falls on that side of the line, unlike the standard `FileVersionInfo` API used for Version/Publisher). Will be picked up by a later DLL/native-dependency-focused phase.
  - `TypeLib` reference is recorded as the raw TypeLib CLSID string only — no deeper type-library parsing (versions, interfaces) is attempted, matching Phase 4B's stated scope.
  - `Description` for the registry's own indirect resource-reference strings (rare for CLSID default values, more common elsewhere) is not resolved — same limitation already documented for the Windows Service Scanner.
- **Security Considerations**: Never activates COM (no `Activator.CreateInstance`/`CoCreateInstance`/`Marshal.GetActiveObject` anywhere in this scanner or its tests), never loads a DLL as code, never executes a `LocalServer32` EXE, never modifies the registry. `LocalServer32` arguments and any raw ambiguous registry value are redacted via `ISecretRedactor` before becoming metadata — never a second redaction implementation.
- **Performance**: Real-machine validated — this dev machine has **14,189** real CLSID registrations (8,031 `Registry64` + 6,143 `Registry32` + 15 `HKCU`, confirmed independently via `Get-ChildItem` before the scanner was written) and a full scan completes in **~5.6 seconds**, well within a 120-second bound the integration test itself asserts. The "check which child keys exist before reading any of them" design (one `GetSubKeyNames` call per CLSID, then only the present children are queried) is what keeps this fast — no unbounded recursive traversal, no redundant reads of known-absent keys.
- **Tests**:
  - `ServerReferenceTests` (7) — quoted/unquoted paths, arguments, unterminated quotes, empty values, ambiguity preservation.
  - `ComClsidReaderTests` (5) — full registration mapping, no-child-keys case, "doesn't query absent child keys" proof, quoted-arguments parsing, per-CLSID `AccessDenied`.
  - `WindowsComScannerBuildEntityTests` (16, pure mapping) — server-type combinations, name fallback chain, CLSID canonicalization, `Installed`/`Registered` status semantics, scope/view metadata per source, distinct-Ids-across-views proof, ambiguous-reference handling, secret redaction (with and without a secret present), no-file-reader-provided graceful skip, registry-Version fallback.
  - `WindowsComScannerScanAsyncTests` (6, fake registry reader) — multiple sources aggregated correctly; same CLSID in two views produces two distinct, non-dropped entities; one-of-many per-CLSID `AccessDenied` → `PartiallySupported` with the rest kept; one whole-source `AccessDenied` → `PartiallySupported` with the other sources kept and an error recorded; all sources `AccessDenied` → `ScannerStatus.AccessDenied` (never `NotInstalled`, never a silent empty result); all sources accessible but empty → `Supported` (never `NotInstalled` — "no COM registered" and "can't read the registry" are different outcomes and must never collapse into one).
  - `WindowsComScanner_AgainstRealMachine_CompletesWithinBoundAndReportsRealCounts` (real machine) — the performance/correctness validation described above, asserting `Status != Failed`, `Status != NotInstalled`, entity count > 1000, and duration < 120s.

## Windows Scheduled Task Scanner (`windows-scheduled-task-scanner`, Phase 4C)

- **Purpose**: Discover Windows Scheduled Tasks — full task path, principal/run-as account, actions (executable/arguments/working directory, including referenced script files), triggers, enabled/disabled state, and last/next run info.
- **Supported Platforms**: Windows.
- **Data Sources**: The native Task Scheduler 2.0 COM API (`Schedule.Service` ProgID), loaded via `Type.GetTypeFromProgID` + `dynamic` — no compile-time COM reference (same reasoning as the Phase 4A IIS provider). Recursively enumerates every task folder from `\`, including hidden tasks (`GetTasks(1)`). Reads: task Path/Name/Enabled/State/LastRunTime/NextRunTime/LastTaskResult; `Definition.RegistrationInfo` (Author/Description); `Definition.Settings` (Hidden/ExecutionTimeLimit); `Definition.Principal` (UserId/RunLevel); `Definition.Actions` (Type/Path/Arguments/WorkingDirectory for Execute actions); `Definition.Triggers` (Type/Enabled/StartBoundary/EndBoundary).
- **Permissions**: No elevation required for standard-user enumeration of tasks visible to that user. AccessDenied is handled at both the whole-service level (connect failure) and per-task/per-folder level (an individual task with restrictive ACLs).
- **Entities Produced**: `ScheduledTask` (existing Phase 1 entity, unchanged). Multiple actions/triggers per task are represented via indexed `Metadata` (see ARCHITECTURE.md addendum) since the base entity's `Action`/`Trigger` fields are singular — they hold the primary (first) one.
- **Evidence Produced**: `ScheduledTask` evidence type, `Location` = full task path.
- **Known Limitations**:
  - `ScriptPathExtractor`'s script-path detection is best-effort regex matching on a script host's arguments (`powershell.exe -File "..."`, `cscript.exe ...`), not a full command-line parser — an unusual invocation form may not be recognized. It never reads the script's contents, only checks existence.
  - `RunLevel`/`LogonType` nuances beyond `LeastPrivilege`/`HighestAvailable` are not deeply modeled — this matches the scope of what migration assessment actually needs (is this task requesting elevated rights or not).
- **Security Considerations**: Strictly read-only — only `Connect`/`GetFolder`/`GetTasks`/`GetFolders`/property getters are ever called; never `RegisterTask`/`Run`/`Stop`/`Delete` or a property setter. The run-as account **name** is captured (`RunAsAccount`) but no credential/password is ever read (Task Scheduler doesn't expose one via this read path). `Description` and action `Arguments` pass through `ISecretRedactor` before becoming metadata.
- **Performance**: No recursive filesystem scanning — folder recursion is scoped entirely to the Task Scheduler's own (typically a few hundred entries) folder tree, not the filesystem. Real-machine validated at 213 tasks in well under a second.
- **Tests**: `ScriptPathExtractorTests` (10) — script-host recognition, quoted/bare script paths, all supported extensions, no-match case. `WindowsScheduledTaskScannerBuildEntityTests` (12, pure mapping) — full task path preservation, Execute action fields, PowerShell script extraction, run-as-account never carrying a credential, disabled-task-still-discovered, running-task status mapping, trigger fields, hex-formatted LastTaskResult, empty actions/triggers, secret redaction, hidden-task metadata, graceful skip without a file reader. `WindowsScheduledTaskScannerScanAsyncTests` (5, fake provider) — AccessDenied, Failed, Supported, PartiallySupported-with-partial-failures-kept, empty-but-Supported. `WindowsScheduledTaskScanner_AgainstRealMachine_DiscoversBuiltInTasks` (real machine) — 213 tasks discovered (179 enabled, 34 disabled), asserting only on the general "built-in `\Microsoft\Windows\...` tasks exist" guarantee, never a specific task name.

## Windows Certificate Scanner (`windows-certificate-scanner`, Phase 4C)

- **Purpose**: Discover certificates in application/server-relevant stores — thumbprint, subject, issuer, validity window, key/signature algorithm details, and expiry risk banding.
- **Supported Platforms**: Windows.
- **Data Sources**: .NET's standard `X509Store`/`X509Certificate2` API (`OpenFlags.ReadOnly`), targeted at four stores only: `LocalMachine\My`, `LocalMachine\WebHosting`, `LocalMachine\Root`, `CurrentUser\My` — not an indiscriminate dump of every store on the machine.
- **Permissions**: No elevation required for standard-user reads of these stores. A store this account can't open (`CryptographicException`) is recorded as `AccessDenied` for that store only; other stores are still read.
- **Entities Produced**: `Certificate` (existing Phase 1 entity, unchanged). Richer fields (SerialNumber, Store, StoreLocation, HasPrivateKey, SignatureAlgorithm, PublicKeyAlgorithm, KeySizeBits, FriendlyName, CertificateStatus, RiskLevel) live in `Metadata`.
- **Evidence Produced**: `CertificateStore` evidence type, `Location` = `{StoreLabel}\{NormalizedThumbprint}`.
- **Expiry/Risk Classification**: performed by a standalone pure helper, `CertificateExpiryClassifier` (not inlined in the scanner, per skill.md §16) — `CertificateStatus` ∈ {`Valid`,`Expired`,`NotYetValid`}, `RiskLevel` ∈ {`Normal`(>90d),`Warning`(31–90d),`High`(8–30d),`Critical`(≤7d or already expired)}. Takes an explicit "as of" time so tests are deterministic and never depend on today's date.
- **Certificate Matching**: `Thumbprint` is normalized (uppercase, whitespace-stripped) on every entity — matching the format `Convert.ToHexString` already produces for the IIS scanner's binding certificate thumbprints (Phase 4A), so a later correlation step can join on `Thumbprint` reliably. Subject/Issuer/FriendlyName are explicitly **not** used as a matching key (skill.md §19 — not guaranteed unique).
- **Known Limitations**:
  - The same logical certificate installed in two different stores produces two distinct entities (`Id` bakes in the store label) — no cross-store merging, matching the same "scanner discovers, Correlation merges" principle used throughout.
  - No `WebSite → USES → Certificate` (or similar) graph edge is built — Phase 5's job. The normalized thumbprint format on both sides is the "lightweight reference" the Phase 4C instructions explicitly allowed.
- **Security Considerations**: Never exports a certificate or accesses private key bytes — `HasPrivateKey` is read from `X509Certificate2.HasPrivateKey` (a boolean flag) only; no `GetRSAPrivateKey()`/`Export(Pfx)`/similar member is ever called anywhere in this scanner or its tests.
- **Performance**: Four targeted stores only, not an enumeration of the full certificate store list on the machine.
- **Tests**: `CertificateExpiryClassifierTests` (10, pure, deterministic dates) — validity window classification, all four risk bands with boundary cases (exactly 90 days, exactly 7 days). `WindowsCertificateScannerBuildEntityTests` (10, pure mapping) — core field mapping, private-key-flag-only guarantee, thumbprint normalization, store/location metadata, distinct-Ids-across-stores-same-thumbprint proof, status/risk-level recording, friendly-name fallback, algorithm/key-size fields, missing-optional-fields robustness. `WindowsCertificateScannerScanAsyncTests` (4, fake provider) — all-accessible, one-store-denied-partial, all-denied, empty-but-accessible. `WindowsCertificateScanner_AgainstRealMachine_DiscoversPublicMetadataOnly` (real machine) — 68 certificates discovered (60 valid, 8 expired, 4 with a private key flag), asserting only on the general "LocalMachine\Root always has trusted CAs" guarantee.

## Windows Runtime/SDK Discovery (`windows-runtime-discovery-scanner`, Phase 4D)

- **Purpose**: Discover installed language runtimes and SDKs across 8 families: .NET Framework, .NET Runtime, .NET SDK, Java (JRE/JDK), Python, Node.js/npm, PHP, Go.
- **Architecture**: One `IRuntimeDetector` per runtime family (`DotNetFrameworkDetector`, `DotNetRuntimeDetector`, `DotNetSdkDetector`, `JavaDetector`, `PythonDetector`, `NodeDetector`, `PhpDetector`, `GoDetector`), orchestrated by `RuntimeDiscoveryScanner` and mapped through one shared `RuntimeEntityBuilder` — see ARCHITECTURE.md's Phase 4D addendum for the full diagram and reasoning. Adding a new runtime family means writing one more detector and registering it in DI; nothing else changes. **As of Phase 6B**, `IRuntimeDetector`/`RuntimeDetectionRow`/`RuntimeDetectionResult`/`RuntimeEntityKind`/`RuntimeEntityBuilder`/`RuntimeDetectionDefaults`/the `dotnet` CLI output-line parser now live in `ServerSleuth.Infrastructure.Runtimes` (moved out of `ServerSleuth.Windows.Runtimes`) so Linux's own runtime detectors reuse the identical model instead of duplicating it — see the Linux Runtime/SDK Discovery section below. `RuntimeEntityBuilder.Build` gained an optional `resolveSource` parameter for this; Windows's own call site passes its existing `EvidenceSources.WindowsRegistry`/`WindowsProcessApi` labels explicitly, so real entity data is unchanged.
- **Supported Platforms**: Windows.
- **Data Sources**:
  - **.NET Framework**: `HKLM\SOFTWARE\Microsoft\NET Framework Setup\NDP\v4\Full` (Release/Version/InstallPath, mapped via Microsoft's own `>=`-threshold table) plus the standalone `v3.5` key (`Install=1`). This key is not WOW64-redirected, so only one registry view is queried.
  - **.NET Runtime/.NET SDK**: `dotnet --list-runtimes` / `dotnet --list-sdks`, `dotnet.exe` located via PATH + `C:\Program Files\dotnet` / `C:\Program Files (x86)\dotnet`. Every output line becomes its own entity.
  - **Java**: `HKLM\SOFTWARE\JavaSoft\{JDK,JRE,Java Development Kit,Java Runtime Environment}` (covering both the Java 9+ and legacy key names) plus `java -version` (executable located via PATH + common vendor install directories: Eclipse Adoptium, Microsoft, Zulu, Amazon Corretto). JDK vs. JRE is determined by checking for a sibling `javac.exe`, never assumed. Vendor is only recorded when the version string contains an explicit textual marker (never guessed from a directory name).
  - **Python**: the `py` launcher's `-0p` listing (the most reliable multi-version mechanism on Windows) plus a scan of known per-version install directories (`Program Files`, `Program Files (x86)`, `%LOCALAPPDATA%\Programs\Python`), each candidate confirmed via `--version`.
  - **Node.js/npm**: `node --version` / `npm --version`, executables located via PATH + `C:\Program Files\nodejs` (both directions).
  - **PHP**: `php --version`, executable located via PATH + `C:\php`, `C:\Program Files\PHP`, `C:\xampp\php`.
  - **Go**: `go version`, executable located via PATH + `C:\Go\bin`, `C:\Program Files\Go\bin`; `GOROOT`/`GOPATH` environment variables recorded (redacted).
- **Permissions**: No elevation required for any of the above. A detector finding nothing reports `NotInstalled` (a normal outcome, not an error, per skill.md §24); a command that fails to execute reports `PartiallySupported` for that family only.
- **Entities Produced**: `Runtime` or `Sdk` (existing Phase 1 entities, unchanged) depending on `RuntimeEntityKind` — an SDK is never reported as a Runtime.
- **Evidence Produced**: `Registry`, `Command`, or `FileSystem`, one per detection source that contributed to a given entity.
- **Multiple Versions & Conflicts**: every distinct version is its own entity (verified: this dev machine reports 6 distinct .NET runtime component/version entities). When registry and command evidence for the same Java installation (`JavaHome`) disagree on version, both observations are preserved via a `ConflictNote` metadata field rather than one being silently chosen.
- **Known Limitations**:
  - Architecture detection is a cheap path-based heuristic (`"Program Files (x86)"` vs. `"Program Files"`), not PE header parsing — the same "DLL deep analysis is out of scope" reasoning as Phase 4B's COM scanner.
  - `ScriptPathExtractor`-style command-line parsing is not needed here since every detector only runs a fixed, argument-free-of-untrusted-data version query — but conversely, a Python/Node/PHP/Go interpreter installed in a genuinely unconventional location (not on PATH, not under any known directory) will not be found; this is an accepted boundary, not a silent failure (the family simply reports `NotDetected`).
  - Java vendor detection only recognizes a fixed set of textual markers (Temurin, Zulu, Corretto, Microsoft Build of OpenJDK, generic OpenJDK, Oracle) — an unrecognized vendor's `Edition` metadata is simply absent, never guessed.
- **Security Considerations**: Every detector runs only a single, hard-coded, argument-free-of-untrusted-input version/list query via `IProcessRunner` with a shared 10-second timeout (`RuntimeDetectionDefaults.CommandTimeout`) — never `npm install`, `pip install`, `dotnet restore`, `dotnet tool install`, or execution of any discovered script/program/application. `GOROOT`/`GOPATH` values pass through `ISecretRedactor` before becoming metadata.
- **Performance**: Real-machine validated at **~0.4–1.0 seconds** for all 8 detectors combined (well within a 60-second bound the integration test asserts) — no filesystem-wide scanning, only targeted PATH/known-directory checks and fixed version-query commands.
- **Tests**: `RuntimeEntityBuilderTests` (11, pure — entity kind selection, status/confidence rules, evidence-per-source, conflict/environment-variable metadata, distinct Ids per version) + `DotNetFrameworkDetectorTests` (8 — release-threshold mapping including the final-version edge case, v3.5 detection, missing-value handling) + `DotNetRuntimeAndSdkDetectorTests` (4 — multi-line parsing, not-found, command-failure-partial, SDK-not-Runtime kind) + `JavaDetectorTests` (6 — registry-only, command-only with JDK/JRE distinction, registry+command merge with and without conflict, not-found) + `PythonDetectorTests` (4 — py-launcher multi-version listing, known-directory fallback, not-found, unusable-path exclusion) + `NodePhpGoDetectorTests` (8 — Node+npm pairing, PHP/Go version parsing, Go environment-variable redaction, not-found cases) + `RuntimeDiscoveryScannerTests` (5 — full aggregation, not-detected-doesn't-degrade-status, partial-with-error, detector-exception-isolation, empty-detector-list) + `RuntimeDiscoveryScanner_AgainstRealMachine_DetectsAtLeastDotNet` (real machine — 15 entities across 6 families discovered in ~0.4s, `Supported`).

## Windows Configuration Scanner (`windows-configuration-scanner`, Phase 4E-1)

> **Phase 6E note**: `ConfigurationFormat`, `ConfigurationParseStatus`, `ScanRoot`, `ConfigurationFileRow`, `ConfigurationAnalysisResult`, `ExternalEndpointReference`, `DatabaseReference`, `UncPathReference`, `ConfigurationFormatDetector`, `ConfigurationContentAnalyzer`, `StructuralValidator`, and the Service/ScheduledTask-derived half of `ScanRootCollector` described below now live in `ServerSleuth.Infrastructure.Configuration`, not `ServerSleuth.Windows.Configuration` — moved so Linux's `linux-configuration-scanner` (see below) could reuse them without a Linux→Windows dependency. `WindowsConfigurationScanner` and its own IIS-aware `ScanRootCollector` wrapper remain in `ServerSleuth.Windows.Configuration`. The move is verified byte-for-byte behavior-preserving (full pre-existing Windows test suite passed unmodified) — everything else in this section is otherwise unchanged from Phase 4E-1/5C.

- **Purpose**: Discover configuration files under application-relevant directories and extract structured facts (secrets present, external endpoints, database references, UNC paths, environment-variable references, runtime references) — never dump raw configuration content into a report.
- **Supported Platforms**: Windows.
- **Scan Root Strategy**: Scan roots are never arbitrary — they come only from entities already discovered by `IisScanner` (`WebSite.PhysicalPath`, `Application.Path`), `WindowsServiceScanner` (`Service.ExecutablePath`'s directory), and `WindowsScheduledTaskScanner` (`ScheduledTask.Action`'s directory, when it's a rooted filesystem path). `ScanRootCollector` deduplicates by normalized path so the same directory is never scanned twice even when two owners point at it (verified: an IIS Site and its root Application pointing at the identical physical path collapse into one scan root).
- **Data Sources**: `*.config`, `*.json`, `*.xml`, `*.ini`, `*.yaml`/`*.yml`, `*.properties` files found (recursively, but only within each already-targeted scan root — never `C:\` or a recursive `Program Files`/`Windows` walk) via Phase 2's `IFileSystemReader.EnumerateFiles`.
- **Supported Formats & Parsing Strategy**:
  - **JSON**: structurally validated via `System.Text.Json.JsonDocument` (BCL, no new package) — a valid document's top-level property names become `DetectedSections`.
  - **XML**: structurally validated via `System.Xml.XmlReader` with `DtdProcessing.Prohibit` and `XmlResolver = null` — hardened against XXE (verified by a test using an actual external-entity payload targeting a local file, which correctly fails to parse rather than resolving the entity).
  - **INI / Properties / YAML**: not structurally parsed (YAML deliberately so, per skill.md §11 — no YamlDotNet or similar large dependency added) — all three, plus any unrecognized extension, are still fully covered by the universal text-based analyzer below.
  - A malformed JSON/XML file gets `ParseStatus = PartiallyParsed` — the structural parse failed, but the text-based analyzer still ran over the raw content, so secrets/endpoints/etc. are still detected even in a broken file.
- **Universal Content Analysis** (`ConfigurationContentAnalyzer`, format-independent): regex-based detection of HTTP/HTTPS/LDAP/LDAPS endpoints (scheme/host/port/path), UNC paths (`\\server\share\...`), `%ENV_VAR%`/`${ENV_VAR}` references, and runtime-family markers (`JAVA_HOME`, `DOTNET_ROOT`, `node_modules`, etc. → `Java`/`DotNet`/`Node`/`Python`/`Php`/`Go`). One implementation covers all formats since these patterns look the same as raw text regardless of surrounding structure.
- **Explicit Target Framework Detection** (`ConfigurationAnalysisResult.RuntimeVersionReferences`, added Phase 5C): a second, narrower regex anchored to a `TargetFramework(s)` key (msbuild XML `<TargetFramework>net8.0</TargetFramework>`, JSON `"TargetFramework": "net8.0"`, or `Key=Value` shapes alike) captures an explicit version-shaped moniker like `net8.0` — deliberately distinct from the family-only markers above, which never carry a version. Added because Phase 5C's Configuration→Runtime correlation must link to a *specific* installed runtime version when one is explicitly named, and must never guess one when only a bare family marker exists; a bare `net8.0`-looking substring with no `TargetFramework` key nearby is never matched, so incidental text (a comment, a URL segment) can't fabricate a version reference.
- **Secret Redaction**: reuses `ISecretRedactor` directly (`ContainsSecret`) — no second redaction implementation. Building this scanner drove two real fixes to `SecretRedactor` itself (Phase 2, see ARCHITECTURE.md decisions log): quoted JSON-style keys and compound camelCase/snake_case keys (`clientSecret`, `accessToken`, `refreshToken`) are now correctly detected.
- **Database Detection**: connection strings are matched by *value shape* (a recognized ADO.NET key — `Server=`, `Data Source=`, `Initial Catalog=`, `Host=`, `Database=`, `Uid=` — followed by `=`), not by requiring adjacency to a `"connectionString"` key name, so nested structures like ASP.NET Core's `"ConnectionStrings": { "Default": "..." }` are still found. Classified into `SqlServer`/`PostgreSql`/`MySql`/`Sqlite`/`Redis`/`Unknown` by which keys are present. **Never captures a credential** — only `Type`/`Host`/`Port`/`Database` are extracted; `Password`/`Uid`/`User Id` values are never read into `DatabaseReference` even though they appear in the source string (verified by a dedicated test).
- **External Endpoint Detection**: `http`/`https`/`ldap`/`ldaps` URIs are parsed into scheme/host/port/path. SMTP and other non-URI-shaped protocol references are a documented limitation (see below).
- **UNC Detection**: `\\SERVER\Share\...` parsed into `Server`/`Share`/`Path` — never accessed.
- **Environment/Runtime References**: recorded as reference names only (e.g. `JAVA_HOME`, `Java`) — never resolved to an actual value, and never claimed as "this configuration uses this runtime" beyond a `ConfigurationReference`-level fact; actual `Application → USES → Runtime` correlation is Phase 5's job.
- **Metadata completeness (Phase 5C additions)**: `Endpoint{i}.Path`, `Database{i}.Port`, and `NetworkPath{i}.Path` are now also persisted to `Configuration.Metadata` alongside the fields already stored since Phase 4E-1 (`Endpoint{i}.Scheme/Host/Port`, `Database{i}.Type/Host/Name`, `NetworkPath{i}.Server/Share`) — these three were captured by `ConfigurationContentAnalyzer` all along but never surfaced to metadata, which blocked Phase 5C's `ExternalDependency` normalization (e.g. a SQL Server port, or a UNC subpath) from being anything but a guess. Purely additive: existing metadata keys/values are unchanged, only new keys are added when the underlying value is present.
- **Ownership**: every `Configuration` entity carries `Metadata["OwnerEntityId"]` set to whichever IIS/Service/ScheduledTask entity's path produced its scan root — `Unknown`/absent when a root has no clear single owner (not currently reachable given the collector's design, but the field is simply omitted rather than invented if it ever were).
- **Large Files**: a 1 MB inspection cap (`WindowsConfigurationScanner.MaxInspectionSizeBytes`) checked via `IFileSystemReader.GetFileInfo` *before* ever reading — an oversized file gets `ParseStatus = SkippedTooLarge` with path/size/timestamp still recorded, and is never analyzed for secrets/references (verified: a 2 MB file is skipped, `SecretDetected` stays `false` because it was never read).
- **Encoding**: no separate encoding-detection code — `IFileSystemReader.ReadTextAsync` (backed by `File.ReadAllTextAsync`) already auto-detects UTF-8, UTF-8 BOM, UTF-16 LE, and UTF-16 BE; verified against real temp files written in each encoding.
- **Known Limitations**:
  - SMTP/other protocol references not expressed as a URI (e.g. a bare `smtpServer`/`mailHost` key with no `smtp://` scheme) are not detected as endpoints — only `http(s)`/`ldap(s)` URIs are.
  - Reparse points/symlinks/junctions are not specially detected or skipped by name — `IFileSystemReader.EnumerateFiles` relies on .NET's own directory enumeration, which does not by default recurse into a junction's target as a separate tree walk in a way that would cause unbounded traversal for the bounded, already-targeted scan roots this phase uses; a dedicated reparse-point detection/skip flag was not implemented as a separate feature.
  - Runtime-reference detection is a fixed keyword list, not exhaustive.
  - Target-framework-version detection (Phase 5C addition) only recognizes `netX[.Y]`-shaped monikers anchored to a `TargetFramework` key — a project using a non-SDK-style `<TargetFrameworkVersion>v4.8</TargetFrameworkVersion>` (older .NET Framework project shape) is not matched by this pattern.
  - Configuration → REFERENCES → {ExternalDependency, Runtime} graph edges are now built, but by `ServerSleuth.Analysis` (Phase 5A/5C), not this scanner — this scanner's job remains populating the `Configuration` entity's own fields/metadata only.
- **Security Considerations**: strictly read-only — never executes configuration, never executes a script referenced by configuration, never connects to a detected database or calls a detected URL, never accesses a detected UNC share, never modifies a file. XML parsing is XXE-hardened. Every value that could be secret-shaped passes through `ISecretRedactor` before ever becoming metadata.
- **Performance**: real-machine validated at **1,516 configuration files** discovered and analyzed in **~11.5 seconds** (474 JSON, 929 XML, 113 INI) — targeted scan roots only, no filesystem-wide walk, files deduplicated by normalized path so a file reachable from two roots is only read once.
- **Tests**: `ConfigurationContentAnalyzerTests` (19 — +5 added in Phase 5C for explicit target-framework detection: 3 TFM shapes correctly detected, bare "net8.0"-looking text with no `TargetFramework` key never matched, a family marker alone never produces a version reference) — endpoint/UNC/env-var/runtime-marker detection, SQL Server/Postgres connection-string classification without credential exposure, secret detection true/false cases, deduplication of repeated endpoints. `StructuralValidatorTests` (13) — valid/malformed JSON and XML, the XXE-rejection test, and format-by-extension mapping. `ScanRootCollectorTests` (8) — per-source root derivation, non-executable scheduled-task actions skipped, deduplication (including case/trailing-slash insensitivity), no-path entities produce no root. `WindowsConfigurationScannerBuildEntityTests` (8, pure mapping) — path/format/owner recording, no-raw-content guarantee, `SkippedTooLarge`/`AccessDenied` handling, dependency-reference summarization, evidence recording. `WindowsConfigurationScannerScanAsyncTests` (7, real temp files) — secret detection end-to-end, UTF-8-BOM and UTF-16 files read correctly, oversized file skipped, malformed JSON still analyzed, multiple files discovered and deduplicated, empty-root handling. Plus `WindowsConfigurationScanner_AgainstRealMachine_CompletesWithoutExposingSecrets` (real machine) — 1,516 real files, 1 real secret detected and confirmed never exposed in any metadata value.

## Windows DLL / Native Dependency Scanner (`windows-binary-discovery-scanner`, Phase 4E-2)

- **Purpose**: Discover native/managed binaries (`.dll`/`.exe`/`.ocx`) from application-relevant roots and extract safe, static PE metadata — architecture, managed-vs-native, imports — without ever loading or executing anything.
- **Supported Platforms**: Windows.
- **Root Strategy**: Reuses Phase 4E-1's `ScanRootCollector` (IIS/Service/ScheduledTask paths) plus a new `ComScanRootCollector` (COM `InprocServer32`/`LocalServer32` directories), merged and deduplicated by normalized path. **Roots under `%windir%` (System32, SysWOW64, WinSxS, ...) are excluded from full directory walks** — see Performance below for why — but a COM-referenced file inside one of those directories is still checked directly, so a dangling/valid reference into a system directory is never silently lost.
- **File Discovery**: `BoundedDirectoryWalker` — a depth-limited (8), file-count-limited (10,000/root) recursive walk that never follows a reparse point/junction/symlink (checked via `IFileSystemReader.IsReparsePoint`, a small addition to the Phase 2 abstraction) and reports `DepthLimitReached`/`FileLimitReached` rather than silently truncating.
- **PE Analysis** (`PeAnalyzer`, backed by the official `System.Reflection.Metadata` `PEReader` — no hand-rolled byte parser): reads PE32/PE32+ magic, COFF machine type (→ `EntityArchitecture`), subsystem, image size, timestamp, and the Import Directory Table (module names only, deduplicated) — all via bounded, on-demand stream reads, never a full in-memory load. Managed-vs-native is `PEReader.HasMetadata` (CLR header presence), never inferred from extension. Delay-imports are recorded as `Unsupported` (skill.md §13's explicit fallback) rather than attempted.
- **Managed/Native/Binary-Type Detection**: `BinaryType` ∈ {`ManagedDll`, `NativeDll`, `Exe`, `Ocx`, `UnknownPe`} — `.ocx` always wins first (COM control), then `PEHeaders.IsExe`, then `.dll` split by `IsManaged`; anything else with a valid PE header is `UnknownPe`. Verified against real files: this repo's own `ServerSleuth.Core.dll` (`ManagedDll`, PE32, Machine=I386 — the standard AnyCPU convention, not a bug), `kernel32.dll` (`NativeDll`, with real imports), `notepad.exe` (`Exe`).
- **Architecture Detection**: from the PE COFF header's `Machine` field only — I386→X86, AMD64→X64, ARM64→Arm64, ARM/ArmThumb2→Arm, anything else→`Unknown`. Never inferred from filename or path.
- **File Metadata**: reuses `IFileVersionMetadataReader` (introduced in Phase 4B for COM) — no second implementation. `FileVersion`/`ProductVersion` → `Dll.Version`, `CompanyName` → `Dll.Publisher`, `ProductName` → metadata.
- **Ownership & Deduplication**: every unique absolute path becomes exactly one `Dll` entity (Phase 1, unchanged) — `Id` is path-based, so the same file discovered via two different sources (e.g. an IIS application's directory walk *and* a direct COM reference) merges into one entity with evidence from both and both owners in `ReferencedByEntityIds`, never two/three separate entities (skill.md §29 — verified by a dedicated test using a real file copied into a temp directory and separately referenced by a synthetic COM registration).
- **Missing References**: a COM registration pointing at a file that no longer exists still produces a `Dll` entity (`Metadata["FileStatus"] = "NotFound"`, `Status = EntityStatus.Unknown`) — valuable migration-risk evidence, never silently dropped (skill.md §16).
- **Evidence**: `FileSystem` evidence per contributing root/reference (`Location` = the file path, `Detail` = which source/reason); an additional `PeMetadata` evidence record when PE analysis succeeded.
- **Known Limitations**:
  - Delay-import parsing is not implemented (`DelayImportAnalysis = "Unsupported"` in metadata) — the explicit fallback skill.md §13 allows; the primary import table already covers the main "what does this binary depend on" question.
  - No managed-assembly reference graph (which other assemblies a managed DLL references) is extracted — skill.md §14 explicitly marks this optional and out of scope for this phase; Phase 5 owns dependency correlation generally.
  - No file hashing (SHA-256 or otherwise) is computed — skill.md §24 explicitly says not to add this unless already required, and it isn't.
  - Reparse-point detection relies on `FileAttributes.ReparsePoint` at the directory-entry level; a reparse point disguised in an unusual way that doesn't set this flag would not be caught (not a realistic scenario on NTFS).
- **Security Considerations**: never `Assembly.LoadFrom`/`LoadLibrary`/`LoadLibraryEx`/`Activator.CreateInstance`/COM activation/`Process.Start` on any discovered binary — verified by inspection of every code path (PE analysis only ever opens a read-only `FileStream` and hands it to `PEReader`, which itself never executes anything). Imported module names pass through `ISecretRedactor` before becoming metadata, consistent with every other scanner.
- **Performance**: **A real, measured problem was found and fixed in this phase.** First real-machine run: 6 minutes 39 seconds, 29,461 binaries — several of Phase 4B's ~14,189 COM registrations resolve into `%windir%\System32`/`SysWOW64`, and fully walking those (thousands of unrelated OS files each) made per-root bounds insufficient in aggregate. Fix (`SystemDirectoryExclusion`): skip full walks of any root under `%windir%`, while still checking the specific COM-referenced file directly. Re-measured: **8.3 seconds**, 18,125 binaries (12,989 managed, 4,247 native, 764 exe, 10 ocx, 43 unknown-PE) — all genuine application/vendor content, no OS noise, comfortably within a 120-second bound the integration test asserts.
- **Tests**: `PeAnalyzerRealFileTests` (5, real files — own managed assembly, `kernel32.dll`, `notepad.exe`, non-existent file, non-PE file) + `BoundedDirectoryWalkerTests` (6, real temp files — depth limit, file limit, extension filtering, empty/non-existent root) + `ComScanRootCollectorTests` (5) + `SystemDirectoryExclusionTests` (4) + `WindowsBinaryDiscoveryScannerBuildEntityTests` (8, pure mapping — found/missing status, multi-root evidence merge, managed/native metadata, redacted imports, delay-import fallback, confidence-from-highest-root) + `WindowsBinaryDiscoveryScannerScanAsyncTests` (4, real temp files + fakes — IIS-root discovery with real PE analysis, dangling COM reference, same-file-two-sources merge, empty-roots case) + `WindowsBinaryDiscoveryScanner_AgainstRealMachine_IsBoundedAndNeverExecutesAnything` (real machine, the performance fix validation above).

# Correlation Layer (Phase 5A, `ServerSleuth.Analysis`)

## CorrelationEngine

- **Purpose**: Turn already-discovered entities (from any combination of scanner `DiscoveryResult`s) into an evidence-backed `DependencyGraph` — never a scanner, never re-invokes discovery, never touches the filesystem/network/registry.
- **Supported Platforms**: Both (plain `net8.0`, no OS dependency — references `ServerSleuth.Core` only).
- **Pipeline**: `DiscoveryEntity[]` → `CorrelationContext` (identity resolution/indexes) → 10 `ICorrelationRule`s → validation (unresolved target / missing endpoint / self-edge / no-evidence all rejected) → `DependencyGraph.AddEdge` (existing Core duplicate-merge logic) → `CorrelationResult { Graph, Diagnostics }`.
- **Identity Resolution**: reuses each scanner's existing `Id` scheme. IIS Site/ApplicationPool membership is read off `Application.ComponentEntityIds` by resolving each id's actual entity type (never a naming-convention guess). Configuration ownership is read off `Configuration.Metadata["OwnerEntityId"]` (assigned unambiguously by Phase 4E-1's `ScanRootCollector`). Binaries are indexed by `WindowsPathNormalizer`-normalized path; certificates by normalized (uppercase, no-whitespace) thumbprint — the same format `WindowsCertificateScanner` already produces.
- **`WindowsPathNormalizer`**: case-folds, trims trailing separators, strips surrounding quotes, normalizes `/` to `\`, and resolves safely-resolvable `%ENVVAR%` references via an injectable `IEnvironmentVariableResolver` (default: `Environment.GetEnvironmentVariable` — a lookup, not execution). Never collapses `Program Files` into `Program Files (x86)`; never merges distinct UNC hosts.
- **`CommandLineReference`**: parses a raw command-line-shaped string (e.g. a Service's registry `ImagePath`) into an executable path + arguments, using the same never-guess-on-ambiguity algorithm as `ServerSleuth.Windows.COM.ServerReference` (Phase 4B), reimplemented rather than referenced so this layer stays platform-agnostic.
- **Relationship Vocabulary**: `DependencyEdgeType` (Core) — `Hosts`, `Uses`, `Contains`* , `Runs`, `References`, `Binds`, `Imports`*, `Configures`*, `DependsOn` (* = added this phase).
- **Rules implemented** (all in `Correlation/Rules/`):
  | Rule | Relationship | Confidence |
  |---|---|---|
  | R1 SiteHostsApplication | Site --Hosts--> Application | VeryHigh |
  | R2 ApplicationUsesApplicationPool | Application --Uses--> ApplicationPool | VeryHigh |
  | R3 ApplicationConfiguresConfiguration | Application --Configures--> Configuration | High |
  | R4 ApplicationContainsBinary | Application --Contains--> Dll | Medium |
  | R5 ServiceRunsBinary | Service --Runs--> Dll | VeryHigh |
  | R6 ScheduledTaskRunsBinary | ScheduledTask --Runs--> Dll | VeryHigh |
  | R7 ComReferencesBinary | ComComponent --References--> Dll | VeryHigh |
  | R8 IisBindingBindsToCertificate | WebSite --Binds--> Certificate | VeryHigh |
  | R9 BinaryImportsBinary | Dll --Imports--> Dll (same-directory-only resolution) | High |
  | R10 ConfigurationReferencesRuntime | Configuration --References--> Runtime | Low |
- **Duplicate Handling**: two rules producing the same logical Source/Target/Type edge merge into one edge with unioned evidence and the higher confidence kept — implemented entirely by `DependencyGraph.AddEdge` (Core, Phase 1), not reimplemented here.
- **No Evidence = No Edge**: any candidate with zero evidence, an unresolved target, a missing source/target entity, or a self-reference is rejected and recorded in `CorrelationDiagnostics.Rejected` with a specific reason — never silently dropped, never guessed into an edge.
- **Known Limitations**:
  - Configuration's Database/Endpoint/UNC references are not correlated into edges — no scanner yet produces those entity types, and creating an edge to a nonexistent node would violate the no-invented-node rule. They remain visible as `Configuration.DetectedDependencyReferences` metadata only.
  - PE import resolution (R9) only ever looks in the importing binary's own directory — an import resolvable via a search-path convention (app-local vs. system-wide vs. SxS) other than "same folder" is left unresolved rather than guessed.
  - Certificate matching (R8) is by thumbprint only, not thumbprint+store — if the identical certificate is installed into two stores, edges are created to both (a genuine multi-target relationship, not a false positive, but not disambiguated by store either).
  - This phase does not build `Application`-level grouping across scanner types (e.g. auto-creating a single logical "ERP application" `Application` entity spanning IIS + Service + Task) — Phase 5A is the correlation *foundation* only, per its own scope boundary.
- **Security Considerations**: purely an in-memory analysis step over data already in hand — no filesystem/registry/network/process access of any kind.
- **Tests**: 67 tests — `WindowsPathNormalizerTests` (9), `CommandLineReferenceTests` (5), `CorrelationContextTests` (3), `CorrelationEngineTests` (7 — no-evidence rejection, self-edge rejection, invalid-target rejection, unresolved-target rejection, duplicate-edge merging, determinism, duplicate-entity-in-input), one test class per rule (10 rules × 2-4 tests each covering the positive case, the negative/ambiguous case, and the specific rule's own edge case), `RealisticErpFixtureTests` (9 — the full synthetic ERP scenario from skill.md §22, asserting every one of the 9 expected relationship kinds and that no edge ever points at a nonexistent node), and `NegativeFixtureTests` (3 — same-filename-different-app, same-display-name-different-identity, COM-registered-with-no-application-evidence).

# Linux Scanners (Phase 6A)

`src/ServerSleuth.Linux/` — targets plain `net8.0`, references `ServerSleuth.Core` + `ServerSleuth.Infrastructure` only (no `ServerSleuth.Windows` dependency). All four scanners are read-only; none ever executes `systemctl start/stop/restart/enable/disable/reload`, writes a unit file, or recursively walks the filesystem.

## Linux OS Scanner (`linux-os-scanner`)

- **Purpose**: Discover the machine's distribution, kernel version, and architecture.
- **Supported Platforms**: Linux.
- **Data Sources**: `/etc/os-release` (primary — `OsReleaseParser`, standard KEY=VALUE format, optionally quoted values); `/proc/sys/kernel/{hostname,osrelease,ostype}` (secondary/fallback, each a single-line file); `uname -m` via `IProcessRunner` (fixed executable, fixed argument, no shell) for architecture only, since no file exposes it.
- **Permissions**: All four sources are world-readable in practice; a missing/unreadable `/etc/os-release` degrades to the `/proc` fallback rather than failing the scan.
- **Entities Produced**: `Server` (Hostname), `OperatingSystem` (Platform/Version/Kernel/Architecture).
- **Evidence Produced**: `FileSystem` evidence for `/etc/os-release` and each `/proc/sys/kernel/*` file read; `Command` evidence for `uname -m` when it succeeded.
- **Known Limitations**: Architecture is `Unknown` (never guessed) if `uname` is unavailable — `Metadata["ArchitectureStatus"] = "Unavailable"` in that case.
- **Security Considerations**: `uname -m` is the only command executed, with a fixed executable/argument list — no discovered/untrusted data is ever passed as an argument.
- **Tests**: `OsReleaseParserTests` (4), `LinuxArchitectureMapperTests` (7 cases), `LinuxOsScannerBuildEntitiesTests` (4, pure mapping), `LinuxOsScannerScanAsyncTests` (3, fakes).

## Linux Process Scanner (`linux-process-scanner`)

- **Purpose**: Discover running processes from `/proc`.
- **Supported Platforms**: Linux.
- **Data Sources**: `/proc/<pid>/status` (Name/State/PPid/Uid), `/proc/<pid>/cmdline` (NUL-separated arguments, joined with spaces), `/proc/<pid>/exe` (symlink target — the executable path). Enumeration is bounded to `/proc`'s own numeric subdirectories (via `IFileSystemReader.EnumerateDirectories`) — never a recursive walk elsewhere.
- **Permissions**: A process owned by another user typically denies `status`/`cmdline`/`exe` access — recorded as `AccessDenied` on that one entity, never aborting the scan. A process that exits between listing and reading (`NotFound`), a zombie (no `exe` target), and a kernel thread (no `exe`, empty `cmdline`) are all handled without exception.
- **Entities Produced**: `Process` (Pid/ParentPid/CommandLine/Path). `StartTime` and per-process `Architecture` are not populated (see Known Limitations).
- **Evidence Produced**: `FileSystem` evidence for `/proc/<pid>/status` and (when resolvable) `/proc/<pid>/exe`.
- **Known Limitations**:
  - `StartTime` is not computed — deriving it from `/proc/<pid>/stat`'s tick-based `starttime` requires assuming the kernel's `CLK_TCK` (not portably discoverable without a syscall), so it is left unset rather than guessed.
  - Per-process architecture (from the executable's ELF header) is not determined — that is static-binary analysis, out of scope for Phase 6A's foundation (a later Linux binary-discovery phase's job, mirroring Windows Phase 4E-2).
  - The real UID is preserved as `Metadata["Uid"]`, never resolved to a username — `/etc/passwd` is outside the phase's allowed read-path list.
- **Security Considerations**: `/proc/<pid>/exe`'s symlink target is read via `FileInfo.LinkTarget` (a single, targeted metadata read) — the executable itself is never opened, loaded, or executed.
- **Tests**: `ProcStatusParserTests` (5), `LinuxProcessScannerBuildEntityTests` (5, pure mapping), `LinuxProcessScannerScanAsyncTests` (4, fake `IProcProvider`), `LinuxProcProviderTests` (6, fake `IFileSystemReader` — the real provider's directory/status/cmdline logic, excluding the symlink-only path which needs a real Linux host).

## Linux Port Scanner (`linux-port-scanner`, backed by `LinuxPortInspector`)

- **Purpose**: Discover listening/bound network endpoints and (where resolvable) their owning process — the second real implementation of Phase 2's cross-platform `IPortInspector`, alongside `WindowsPortInspector`.
- **Supported Platforms**: Linux.
- **Data Sources**: `/proc/net/tcp`, `/proc/net/tcp6`, `/proc/net/udp`, `/proc/net/udp6` (`ProcNetParser` — hex-encoded local address/port, kernel byte order). TCP rows are included only in the `LISTEN` (`0A`) state; UDP rows are always included (UDP has no listen concept). Ownership resolution (`SocketOwnershipResolver`) walks `/proc/<pid>/fd/*` symlinks shaped `socket:[inode]` to build an inode→PID map.
- **Permissions**: A `tcp6`/`udp6` source missing (IPv6 disabled) is not an error — simply no rows from that source. A process's `fd` directory unreadable (owned by another user) contributes nothing to the ownership map; the port's `OwningPid` stays `null` — never guessed from a process's command line containing a similar port number.
- **Entities Produced**: `Port` (Protocol/LocalAddress/Number/OwningPid).
- **Evidence Produced**: `NetworkSocket` evidence citing the specific `/proc/net/*` source and (when resolved) the owning PID.
- **Known Limitations**: Ownership resolution requires reading `/proc/<pid>/fd` for every PID on the system for every port scan — potentially many entries — but only ever enumerates within `/proc`, never elsewhere.
- **Security Considerations**: Never `netstat`/`ss`/`lsof` — implemented directly against `/proc/net/*` and `/proc/<pid>/fd/*`.
- **Tests**: `ProcNetParserTests` (5, including a verified IPv4 and IPv6 address decoding), `SocketOwnershipResolverTests` (3, bounded-enumeration/permission paths — the symlink-target path needs a real Linux host), `LinuxPortInspectorTests` (5, fakes), `LinuxPortScannerTests` (4).

## Linux systemd Service Scanner (`linux-systemd-service-scanner`, backed by `SystemctlProvider`)

- **Purpose**: Discover systemd service units — unit name, description, load/active/sub state, enabled/disabled, `ExecStart`, running-as user, working directory, and unit file path.
- **Supported Platforms**: Linux.
- **Data Sources**: `systemctl list-units --type=service --all --output=json` (a genuine JSON array — `unit`/`load`/`active`/`sub`/`description`) for the unit list, then `systemctl show <unit> --property=...` (`Key=Value` per line) per unit for everything else. Both are machine-readable; `systemctl status`'s human-formatted prose is never parsed.
- **Permissions**: `systemctl` missing → `NotInstalled`. A `show` failure for one specific unit is recorded as a partial failure (that unit's row is still produced, marked `DetailUnavailable`) — never aborts the whole scan.
- **Entities Produced**: `Service` (DisplayName/StartType/ServiceAccount/ExecutablePath/CommandLineArguments), `Status` = Running (ActiveState=active) / Configured (LoadState=loaded) / Unknown (not-found).
- **Evidence Produced**: `ServiceConfiguration` evidence citing the unit name; `ConfigurationFile` evidence citing the unit file path (`FragmentPath`) when available.
- **Known Limitations**: `ExecutablePath` is only populated when `ExecStart`'s `path=...` shape is recognized — an unusual/templated `ExecStart` yields `Metadata["ExecutablePathStatus"] = "Unrecognized ExecStart shape"` rather than a guessed path.
- **Security Considerations**: Only `list-units` and `show` are ever invoked — never `start`/`stop`/`restart`/`enable`/`disable`/`reload`, and no unit file is ever written.
- **Tests**: `SystemctlKeyValueParserTests` (3), `ExecStartParserTests` (3), `LinuxSystemdServiceScannerBuildEntityTests` (6, pure mapping — active/inactive/not-found/detail-unavailable/unrecognized-ExecStart/multiple-services), `LinuxSystemdServiceScannerScanAsyncTests` (6, fakes — NotInstalled/AccessDenied/Failed/Available/partial-failure/empty), `SystemctlProviderTests` (5, fake `IProcessRunner` — the real provider's list+show merge logic).

## Linux Package Scanner (`linux-package-scanner`, Phase 6B)

- **Purpose**: Discover installed packages across every available package manager (dpkg/rpm/apk) — never assumes the distribution from `/etc/os-release` first.
- **Supported Platforms**: Linux.
- **Architecture**: One `IPackageManagerProvider` per manager (`DpkgPackageProvider`, `RpmPackageProvider`, `ApkPackageProvider`), orchestrated by `LinuxPackageScanner` — mirrors the `IRuntimeDetector`-per-family pattern from Windows Phase 4D. Adding a new manager means writing one more provider and registering it in DI.
- **Data Sources**:
  - **dpkg** (Debian/Ubuntu): `dpkg-query -W -f='${Package}\t${Version}\t${Architecture}\t${Maintainer}\n'` — a fixed, machine-readable format string, never `apt`/`apt-get`.
  - **rpm** (RHEL/Fedora/openSUSE/etc.): `rpm -qa --queryformat '%{NAME}\t%{VERSION}-%{RELEASE}\t%{ARCH}\t%{VENDOR}\t%{SOURCERPM}\n'` — never `dnf`/`yum`/`zypper`. rpm's `(none)` placeholder for an absent field is normalized to `null`, never stored as literal text.
  - **apk** (Alpine): `apk info -v`, which has no per-field format option — name/version are split via `ApkPackageLineParser`'s reliance on Alpine's own `-r<release>` suffix convention (verified against `musl-1.2.4-r2`, `ca-certificates-20230506-r0`, etc.), never a naive last-hyphen split.
- **Permissions**: A missing package-manager executable is `NotInstalled` for that one manager only (a normal outcome — most systems only have one of the three installed). A malformed output line is skipped, never fails the whole scan.
- **Entities Produced**: `Package` (existing Phase 1 entity, unchanged) — `PackageManager` records which of the three found it.
- **Deduplication & Identity**: `package:{manager}:{name}:{version}:{architecture}`, deduplicated within one manager's own results only — `dpkg`'s and `rpm`'s `openssl` are never merged just because the name matches (skill.md §8), since they are genuinely different packages.
- **Evidence Produced**: `PackageManager` evidence citing which manager and the package name.
- **Known Limitations**: `InstallPath`/`Description` are rarely reliably available from any of the three managers' fixed-format queries and are typically absent (never guessed). `apk`'s Maintainer/Description fields are not queried at all, since `apk info -v` doesn't expose them without a second, less reliable command.
- **Security Considerations**: Only read-only query subcommands are ever invoked (`-W`, `-qa`, `info -v`) — never `install`/`upgrade`/`remove`/`add`/`del` for any of the three managers, and no shell is ever used.
- **Tests**: `ApkPackageLineParserTests` (5, including the negative "unrecognized shape" case), `DpkgPackageProviderTests` (3), `RpmPackageProviderTests` (4, including the `(none)`-as-null case), `ApkPackageProviderTests` (2), `LinuxPackageScannerTests` (6 — pure mapping, cross-manager aggregation, within-manager deduplication, cross-manager non-merging, AccessDenied handling, all-managers-absent).

## Linux Runtime/SDK Discovery (`linux-runtime-discovery-scanner`, Phase 6B)

- **Purpose**: Discover installed language runtimes/SDKs across 7 families: .NET Runtime, .NET SDK, Java, Python, Node.js/npm, PHP, Go — the Linux counterpart to Windows Phase 4D, sharing its entity model rather than duplicating it.
- **Supported Platforms**: Linux.
- **Architecture**: One `IRuntimeDetector` per family (`DotNetRuntimeDetector`, `DotNetSdkDetector`, `JavaDetector`, `PythonDetector`, `NodeDetector`, `PhpDetector`, `GoDetector`), orchestrated by `LinuxRuntimeDiscoveryScanner`. All of `IRuntimeDetector`/`RuntimeDetectionRow`/`RuntimeDetectionResult`/`RuntimeEntityKind`/`RuntimeEntityBuilder`/`RuntimeDetectionDefaults`/the `dotnet` CLI output parser are the *same* types Windows's detectors use — extracted to `ServerSleuth.Infrastructure.Runtimes` this phase specifically so this scanner never duplicates that logic (see ARCHITECTURE.md's Phase 6B addendum). Linux has its own `IExecutableLocator`/`LinuxExecutableLocator` (`:`-separated PATH, no file-extension matching) — genuinely different from Windows's, not shared.
- **Data Sources**:
  - **.NET Runtime/SDK**: `dotnet --list-runtimes` / `dotnet --list-sdks`, `dotnet` located via PATH + `/usr/share/dotnet`, `/usr/lib/dotnet`, `/opt/dotnet`.
  - **Java**: `java -version` only (no registry on Linux) — executable located via PATH + common JVM directories; JDK vs. JRE determined by checking for a sibling `javac`, never assumed.
  - **Python**: every `python3*` executable found in `/usr/bin`, `/usr/local/bin`, `/opt/python/bin` (plus a direct PATH lookup) is confirmed independently via `--version` and becomes its own entity — `python3`, `python3.10`, `python3.11` are never merged into one (skill.md §14).
  - **Node.js/npm**: `node --version` / `npm --version`, located via PATH + `/usr/bin`, `/usr/local/bin`, `/opt/nodejs/bin`.
  - **PHP**: `php --version`, located via PATH + `/usr/bin`, `/usr/local/bin`, `/opt/php/bin`.
  - **Go**: `go version`, located via PATH + `/usr/local/go/bin`, `/usr/bin`, `/opt/go/bin`; `GOROOT`/`GOPATH` recorded (redacted).
- **Permissions**: A family found nowhere reports `NotInstalled` (normal, not an error); a command that fails to execute reports `PartiallySupported` for that family only.
- **Entities Produced**: `Runtime` or `Sdk` (Phase 1, unchanged) — every distinct version is its own entity, never collapsed.
- **Evidence Produced**: `Command` evidence per detection (Linux has no registry source, unlike Windows).
- **Known Limitations**: Same architecture-detection boundary as Windows — no ELF header parsing is performed (out of scope, mirrors the "no PE deep analysis" boundary from Phase 4B/4D).
- **Security Considerations**: Every detector runs only a single, fixed, argument-free-of-untrusted-input version/list query via `IProcessRunner` (shared 10-second timeout) — never `pip install`, `npm install`, `dotnet restore`, `dotnet tool install`, `go install`, `gem install`, or execution of any discovered program.
- **Tests**: `DotNetRuntimeAndSdkDetectorTests` (4 — multi-version aggregation never collapsed, not-found, SDK-kind, command-timeout-partial), `JavaDetectorTests` (3 — JDK-via-javac, JRE-only, not-found), `PythonDetectorTests` (3 — multi-interpreter never-merged, none-found, unusable-path-excluded), `NodePhpGoDetectorTests` (6 — Node+npm pairing, PHP version parsing, Go env-var redaction, not-found cases), `LinuxRuntimeDiscoveryScannerTests` (3 — aggregation, partial-on-detector-failure, empty-result).

## Linux Scheduled Task Scanner (`linux-scheduled-task-scanner`, Phase 6B)

- **Purpose**: Discover cron-based scheduled jobs from a fixed, bounded set of well-known locations.
- **Supported Platforms**: Linux.
- **Data Sources** (all read-only, no recursive walk of unrelated directories): `/etc/crontab` and `/etc/cron.d/*` (system-style, 6 fields including a user column); `/etc/cron.{hourly,daily,weekly,monthly}/*` (run-parts convention — each file itself IS the job; the directory name alone supplies the trigger, no line parsing); `/var/spool/cron/crontabs/*` (Debian-style user crontabs, 5 fields, filename = username) with `/var/spool/cron/*` (RHEL-style) as a fallback when the Debian-style directory doesn't exist.
- **Parsing**: `CronLineParser` recognizes comments, blank lines, and environment-variable assignment lines (`PATH=...`, `MAILTO=""`) and skips them rather than misparsing them as malformed jobs; both 5-field (user crontab) and 6-field (system crontab) formats are supported, plus the `@reboot`/`@daily`/etc. macro shorthand. A line matching neither shape is simply skipped, never guessed at.
- **Entities Produced**: `ScheduledTask` (existing Phase 1 entity, unchanged) — `Folder` = source file path, `Trigger` = schedule expression (or run-parts interval name), `Action` = extracted executable path (or the redacted full command if unresolved), `RunAsAccount` = user, `Enabled` = true.
- **Command Path Extraction**: `CronCommandPathExtractor` only ever recognizes an explicit leading absolute path (`/opt/erp/bin/worker ...`) — a bare command name (`python3 script.py`, resolvable only via a PATH lookup this tool cannot statically know) or shell-chained command (`cd / && ...`, requiring shell-syntax evaluation) is left unresolved (`Metadata["ExecutablePathStatus"] = "Unresolved"`) rather than guessed.
- **Secret Handling**: every raw command is passed through the existing `ISecretRedactor` (Phase 2) before being stored as `Metadata["Command"]` — the raw value is never persisted; `SecretDetected` metadata is set when a secret-shaped substring was found.
- **Permissions**: A source not present at all (`NotFound`) is normal and silently skipped; `AccessDenied` on a source is recorded as a `DiscoveryError` and degrades the scanner to `PartiallySupported`.
- **Duplicate Handling**: identity is `scheduledtask:cron:{sourceFile}:{lineIndex}` (or `scheduledtask:cron:{filePath}` for run-parts entries) — the identical schedule+command appearing in two different source files produces two distinct entities, never incorrectly merged into one.
- **Security Considerations**: Never runs a cron command, never evaluates shell syntax/substitutions, never resolves credentials — purely reads and parses text.
- **Tests**: `CronLineParserTests` (10 — system/user formats, macro shorthand, all skippable-line variants, malformed-too-few-fields for both formats), `CronCommandPathExtractorTests` (4), `LinuxScheduledTaskScannerBuildEntityTests` (4 — explicit path extraction, unresolved-command metadata, secret redaction, cross-file distinct-identity), `LinuxScheduledTaskScannerScanAsyncTests` (7 — `/etc/crontab` multi-job, `/etc/cron.d`, `cron.daily` run-parts, Debian-style user crontab, permission-denied source, no-sources-present, identical-job-in-two-files-never-merged).

## Linux Container Scanner (`linux-container-scanner`, Phase 6C)

- **Purpose**: Discover Docker and Podman containers, images, volumes, and networks, read-only — the Linux counterpart to no direct Windows equivalent this project has built yet.
- **Supported Platforms**: Linux.
- **Architecture**: One `IContainerRuntimeProvider` per runtime (`DockerContainerRuntimeProvider`, `PodmanContainerRuntimeProvider`), both thin public wrappers over an internal shared `ContainerCliRuntimeProvider` parametrized only by executable name (`docker`/`podman`) — their read-only CLI/JSON output is compatible enough that duplicating the parsing logic per runtime would have violated the "reuse, don't duplicate" instruction. `LinuxContainerScanner` orchestrates both providers and maps their snapshots to entities.
- **Data Sources** (all read-only; every command runs through `IProcessRunner` with discrete argument lists, never a shell string):
  - **Containers**: `ps -aq --no-trunc` to list all container IDs (running and stopped), then one bulk `inspect id1 id2 ...` call returning a JSON array — never N+1 calls.
  - **Images**: `images --no-trunc --format {{json .}}` (one JSON object per line, parsed independently so a malformed line never fails the whole scan).
  - **Volumes**: `volume ls --format {{json .}}`; Docker emits `Labels` as a comma-separated string here (unlike the dictionary shape `inspect` uses for container labels) so a dedicated `ParseLabelString` parser is used.
  - **Networks**: `network ls -q --no-trunc` for IDs, then bulk `network inspect id1 id2 ...`; Subnet/Gateway extracted from `IPAM.Config[0]`, attached container names from the `Containers` dict's values.
  - Podman uses the identical command set via the same shared provider, parametrized with `podman` as the executable.
- **Runtime Detection**: `ContainerRuntimeAvailability` (`Supported`/`PartiallySupported`/`NotInstalled`/`AccessDenied`/`Unavailable`) is classified from actually querying the runtime — process start failure (`OperationStatus.StartFailed` **or** `OperationStatus.NotFound` — see the Phase 6G real-Linux fix note below) → `NotInstalled`; stderr containing "permission denied" (case-insensitive, verified against both Docker's socket-permission phrasing and Podman's rootless phrasing) → `AccessDenied`; any other non-zero exit → `Unavailable`. The `docker`/`podman` executable merely existing on PATH is never treated as "supported" — only an actual successful query counts. Podman with zero containers is correctly `Supported` with zero entities, not conflated with "not installed." **Phase 6G fix**: this classification originally checked only `OperationStatus.StartFailed`, but the real `ProcessRunner` reports a genuinely-missing executable as the more specific `OperationStatus.NotFound` — a real Podman-absent WSL Ubuntu machine surfaced this as a misclassification to `Unavailable` before the fix (see PROGRESS.md's Phase 6G entry).
- **Entities Produced**: `Container` (existing Phase 1 entity, unchanged) reused via a `Type` discriminator for all four kinds — `"Container"`, `"Image"`, `"Volume"`, `"Network"`. No `DockerContainer`/`PodmanContainer` types were introduced.
  - **Container**: `ContainerId`, `Name`, `ImageTag` (`repository:tag`), `Created`, `State` (normalized to `Running`/`Configured` — `running` → `Running`, everything else including `exited`/`paused`/`restarting`/`dead`/`created` → `Configured`, raw state preserved in metadata), `RestartPolicy`, redacted `Entrypoint`/`Command`, port mappings (`HostAddress`/`HostPort`/`ContainerPort`/`Protocol`, including exposed-but-unpublished ports), mounts (`Type`/`Source`/`Destination`/`ReadOnly`/`Propagation`, as per-mount metadata), `EnvironmentVariableNames` (names only), and redacted per-label metadata.
  - **Image**: Repository, Tag, ImageId, Created, `SizeDisplay` (Docker's raw human-formatted string, e.g. `"142MB"` — not converted to bytes, since the listing call doesn't expose a raw byte value).
  - **Volume**: Name, Driver, Mountpoint, redacted labels.
  - **Network**: NetworkId, Name, Driver, Subnet, Gateway, attached container names.
- **Identity & Deduplication**: `container:{runtime}:{id}`, `image:{runtime}:{id}`, `volume:{runtime}:{name}`, `network:{runtime}:{id}` — always runtime-qualified so a Docker and a Podman entity with a coincidentally-identical ID never collide.
- **Secret Handling**: Environment variable **values are never stored** — only the variable name (split on the first `=`) is kept in `EnvironmentVariableNames`. Labels, Entrypoint, and Command are passed through `ISecretRedactor` (Phase 2) before being stored as metadata.
- **Permissions**: `NotInstalled` for a runtime not present is normal (most systems have at most one of Docker/Podman); `AccessDenied`/`Unavailable` are recorded as a `DiscoveryError` and degrade the scanner to `PartiallySupported`; a container-level `inspect` failure amid an otherwise-successful run is recorded as a partial failure without discarding the containers that did succeed.
- **Correlation Boundary**: No `Container → host Process` relationship is inferred from PID/command-line/port similarity alone — that correlation, if ever performed, belongs to Phase 5 analysis and only when explicit namespace evidence exists. The container's own reported PID (when exposed by `inspect`) is captured as a fact, nothing more.
- **Security Considerations**: Only read-only subcommands are ever invoked — never `exec`/`run`/`start`/`stop`/`restart`/`rm`/`pull`/`push`/`build`/`commit`/`kill`/`pause`/`unpause`, never `sh -c`/`bash -c` or any shell, never a direct read of `/var/run/docker.sock` or an HTTP request to it, never a recursive scan of `/var/lib/docker`/`/var/lib/containers`. No discovered container data (image names, labels, env values) is ever interpolated into an executable command argument.
- **Known Limitations**: Image `OS`/`Architecture` are not populated (`docker images --format json` doesn't expose them; a second per-image `inspect` call was judged out of scope). No `Container → host Process` correlation performed (deliberately deferred). No real-machine validation performed on this Windows development host.
- **Tests**: `ContainerRuntimeProviderTests` (15 — Docker/Podman container parsing incl. env/labels/mounts/ports, NotInstalled, Unavailable, AccessDenied for both runtimes' phrasing, empty-result Supported, multiple containers, missing image reference never guessed, image/volume/network listing parsing, malformed image line skipped, partial inspect failure recorded without losing other data), `LinuxContainerScannerBuildEntityTests` (12 — running/exited status mapping, env names-only, label/entrypoint/command redaction, deterministic + runtime-distinct IDs, mount metadata, image/volume/network entity mapping), `LinuxContainerScannerScanAsyncTests` (5 — Docker-only Supported, both-runtimes aggregation, neither-installed → NotInstalled, AccessDenied → PartiallySupported with permission error, images/volumes/networks all produce entities), `ContainerRuntimeNegativeSecurityTests` (4 — asserts via `FakeProcessRunner.Invocations` that no forbidden subcommand, shell executable, or non-runtime executable is ever invoked).

## Linux Kubernetes Scanner (`linux-kubernetes-scanner`, Phase 6D)

- **Purpose**: Discover a Kubernetes cluster's Namespaces, Nodes, Pods (+ containers), Deployments/StatefulSets/DaemonSets, Services, Ingresses, ConfigMaps, Secrets (metadata only), PersistentVolumeClaims, and PersistentVolumes via the currently configured `kubectl` context, read-only throughout.
- **Supported Platforms**: Linux.
- **Architecture**: `IKubernetesProvider` → `KubectlKubernetesProvider` → `LinuxKubernetesScanner`, a single-implementation instance of the same provider-based pattern used since Phase 4D — there is only one Kubernetes acquisition path (kubectl), unlike Phase 6C's Docker/Podman split.
- **Data Sources** (all read-only, one fixed bulk call per resource kind — never one call per object):
  - `kubectl version -o json` — the availability gate; also supplies `ServerVersion`.
  - `kubectl config current-context` — best-effort; failure never affects availability classification, only leaves `Cluster.ContextName` unset.
  - `kubectl get namespaces -o json`, `kubectl get nodes -o json`, `kubectl get pv -o json` (cluster-scoped).
  - `kubectl get pods|deployments|statefulsets|daemonsets|services|ingress|configmaps|secrets|pvc --all-namespaces -o json` (namespace-scoped, all namespaces in one call).
- **Runtime Detection**: `KubernetesAvailability` (`Supported`/`PartiallySupported`/`NotInstalled`/`AccessDenied`/`Unavailable`) is classified from the result of `kubectl version -o json` actually querying the server — process start failure (`OperationStatus.StartFailed` **or** `OperationStatus.NotFound` — see the Phase 6G real-Linux fix note below) → `NotInstalled`; stderr containing "forbidden"/"permission denied"/"Unauthorized" → `AccessDenied`; any other failure (e.g. connection refused/timeout) → `Unavailable`. `kubectl` merely existing on PATH is never treated as "Kubernetes available." **Phase 6G fix**: this classification originally checked only `OperationStatus.StartFailed`, but the real `ProcessRunner` reports a genuinely-missing executable as the more specific `OperationStatus.NotFound` (never exercised by `FakeProcessRunner`'s hard-coded StartFailed default) — a real WSL Ubuntu machine with `kubectl` genuinely absent surfaced this as `Failed` instead of `NotInstalled` before the fix (see PROGRESS.md's Phase 6G entry).
- **Entities Produced**:
  - `Cluster` — ServerVersion, ContextName, IsCurrentContext, ClusterIdentifier (only populated from the `kube-system` namespace's own UID when present — never invented).
  - `KubernetesNamespace` — Phase, Uid, labels as metadata.
  - `KubernetesNode` — Roles (from `node-role.kubernetes.io/<role>` labels), KubernetesVersion (kubelet version), OsImage, ContainerRuntimeVersion, KernelVersion, Ready.
  - `KubernetesPod` — Namespace, Uid, Phase, NodeName, PodIp, HostIp (recorded as facts only — never probed, never connected to).
  - `Container` (Type = "KubernetesContainer") — one per pod container, reusing the existing Phase 1 model; never merged with a host-level Docker/Podman container from the Phase 6C scanner.
  - `KubernetesWorkload` (Kind = "Deployment"/"StatefulSet"/"DaemonSet") — DesiredReplicas, ReadyReplicas, SelectorLabels, TemplateContainerImages.
  - `KubernetesService` — ServiceType, ClusterIp, ExternalIps, Ports (display strings), SelectorLabels — no network probe, no listening-process inference.
  - `KubernetesIngress` — IngressClassName, Hosts, Paths (display strings), TlsSecretNames — never contacted, never DNS-resolved, never certificate-validated.
  - `KubernetesConfigMap` — Keys (text + binary key names); text values redacted via `ISecretRedactor` before storage as metadata; binary values never captured at all.
  - `KubernetesSecret` — Namespace, SecretType, Keys **only** — see Security Considerations below.
  - `KubernetesPersistentVolumeClaim` — Phase, Capacity, AccessModes, StorageClassName, VolumeName, VolumeMode.
  - `KubernetesPersistentVolume` — Phase, Capacity, AccessModes, StorageClassName, ReclaimPolicy, VolumeSourceType, HostPath (declared path string only — never accessed, never recursively scanned, symlinks never followed).
- **Identity & Deduplication**: every entity ID includes the cluster's context name (`cluster:{context}`, `namespace:{context}:{name}`, `pod:{context}:{uid-or-namespace/name}`, `podcontainer:{context}:{pod-key}:{containerName}`, `workload:{context}:{kind}:{namespace}:{uid-or-name}`, etc.) so scanning multiple clusters/contexts in one process never merges same-named resources across clusters (skill.md §22).
- **Secret Handling (CRITICAL)**: `KubernetesSecret` never captures values — the provider's internal `SecretItem.Data` DTO is typed `Dictionary<string, JsonElement>` specifically so a base64 value is never materialized as a usable string, let alone decoded or stored; only `.Keys` is ever read. Verified by a dedicated test asserting the resulting `KubernetesSecret` entity carries **zero** metadata and that no known secret value appears anywhere in the full scan's entities/metadata/evidence.
- **Permissions**: `NotInstalled`/`AccessDenied`/`Unavailable` map to `ScannerStatus.NotInstalled`/`AccessDenied`/`Failed` respectively with a recorded `DiscoveryError` (except `NotInstalled`, which is a normal, error-free outcome); a single resource kind's query failure amid an otherwise-successful run is recorded as a partial failure (including a malformed top-level JSON response) without discarding the resource kinds that did succeed, degrading the scanner to `PartiallySupported`.
- **Correlation Boundary**: No `KubernetesPod`/`KubernetesContainer` → host Process/Container relationship is inferred — that correlation, if ever performed, belongs to Phase 5 analysis, mirroring the exact boundary Phase 6C drew for Docker/Podman.
- **Security Considerations**: Only read-only `kubectl get`/`version`/`config current-context` subcommands are ever invoked — never `exec`/`cp`/`apply`/`create`/`delete`/`patch`/`edit`/`rollout`/`port-forward`/`replace`, never `sh -c`/`bash -c` or any shell. No kubeconfig credentials (client certs/keys/tokens/passwords) are ever read, dumped, or persisted — the scanner relies entirely on kubectl's own already-configured context. No PV/Pod hostPath is ever accessed, read, or recursively scanned.
- **Known Limitations**: Node role extraction only recognizes the `node-role.kubernetes.io/<role>` label convention (not the older `kubernetes.io/role` shape). PV volume-source-kind detection recognizes a fixed list of common source keys; an unrecognized kind is left `null`. `Cluster.ClusterIdentifier` is only populated when a `kube-system` namespace exists in the namespaces result. No real-cluster validation performed on this Windows development host.
- **Tests**: `KubectlKubernetesProviderTests` (21 — kubectl not installed, version-query AccessDenied/Unavailable, all-empty Supported with version/context, multi-namespace with kube-system-derived cluster identifier, node role/version extraction, pod phase/IP/container parsing, Deployment/StatefulSet/DaemonSet parsing across their three distinct JSON shapes, Service port/selector parsing, Ingress host/path/TLS-secret parsing, ConfigMap key+text-value parsing, Secret key-names-only parsing, PVC parsing, PV hostPath/NFS volume-source detection, malformed JSON skipped without failing the whole scan, one resource's failure not blocking others, 500-item large list, duplicate-named resources across namespaces), `LinuxKubernetesScannerBuildEntityTests` (16), `LinuxKubernetesScannerScanAsyncTests` (6), `KubernetesNegativeSecurityTests` (4 — no forbidden subcommand, no shell executable, exactly one bulk call per resource kind, no secret value anywhere in metadata/evidence across a full scan). 47 tests total in the `Kubernetes/` folder, plus one `ServiceCollectionExtensionsTests` case whose name also matches a "Kubernetes" filter.

## Linux Configuration Scanner (`linux-configuration-scanner`, Phase 6E)

- **Purpose**: Discover configuration files under bounded, known Linux locations and extract structured facts — the Linux counterpart to `windows-configuration-scanner`, answering "where is this server configured, and what configuration files define the discovered services/workloads?"
- **Supported Platforms**: Linux.
- **Architecture**: `LinuxScanRootCollector` → `LinuxConfigurationScanner`, with technology-specific fact extraction delegated to `LinuxConfigurationTechnologyAnalyzer`. Reuses the Phase 6E-extracted, platform-neutral `ServerSleuth.Infrastructure.Configuration` types (`ConfigurationFormat`, `ConfigurationFileRow`, `ConfigurationAnalysisResult`, `ConfigurationContentAnalyzer`, `StructuralValidator`, `ScanRootCollector`'s Service/ScheduledTask-derived pieces) rather than duplicating them. Re-runs `LinuxSystemdServiceScanner` and `LinuxScheduledTaskScanner` directly (both also registered as their own concrete types in DI, mirroring Windows's `IisScanner`/`WindowsServiceScanner` pattern) purely to obtain executable paths for application scan roots — never duplicating their own discovery logic.
- **Bounded Root Strategy** (skill.md (Phase 6E) §3-6 — never a recursive filesystem-wide walk):
  - **Well-known technology directories** (always added, existence checked only at enumeration time so a missing directory is simply `NotFound`, never an error): `/etc/systemd/system`, `/usr/lib/systemd/system`, `/lib/systemd/system` (systemd); `/etc/nginx`; `/etc/apache2`, `/etc/httpd` (Apache); `/etc/php`; `/etc/mysql`; `/etc/postgresql`; `/etc/docker`; `/etc/ssh`.
  - **Application roots**, derived from already-discovered `Service.ExecutablePath` (systemd units) and `ScheduledTask.Action` (cron jobs, only when the action is an already-resolved rooted path): the executable's own containing directory, UNLESS that directory's final path segment is exactly `bin` or `sbin` — the ubiquitous `/opt/app/bin/executable` convention — in which case the scan root climbs exactly **one** level to the parent (e.g. `/opt/erp/bin/erp` → `/opt/erp`), and never climbs to `/` itself even if that one-level climb would land there. This rule is fixed and deterministic — no directory name other than `bin`/`sbin` ever triggers a climb, and it never climbs more than once.
  - **Deliberately excluded**: `/etc/cron.d` is never added as a root, even though §4 lists it among "well-known" candidates — Phase 6B's `LinuxScheduledTaskScanner` already owns those files as `ScheduledTask` entities, and scanning them again here would produce a duplicate `Configuration` entity for the exact same file with no new information (§4's own header text explicitly says not to duplicate Phase 6B's cron responsibilities).
  - Deduplication is by **case-sensitive** path comparison (`StringComparer.Ordinal`) — Linux paths are never lower-cased, unlike Windows's `OrdinalIgnoreCase` collector.
- **Data Sources**: `*.json`, `*.xml`, `*.ini`, `*.yaml`/`*.yml`, `*.properties`, `*.env`, `*.conf`, `*.cnf`, `*.service`/`*.socket`/`*.timer`/`*.mount`/`*.target`/`*.path`/`*.slice` (systemd unit-file extensions), and the exact filename `sshd_config` (which has no extension) — searched recursively but only within each already-targeted bounded root.
- **Per-Technology Fact Extraction** (`LinuxConfigurationTechnologyAnalyzer`, dispatched by the file's `ScanRoot.Source`, always in ADDITION to the generic cross-format analysis below — conservative line/regex extraction, never a full grammar parser, per skill.md §7):
  - **systemd** (§16-17): `Description`, `ExecStart`, `User`, `WorkingDirectory`, `Restart`, `After`, `Requires`, `Wants`, and every `EnvironmentFile=` line (indexed `EnvironmentFile0`, `EnvironmentFile1`, ... — a leading `-` "ignore if missing" marker is stripped, never treated as part of the path). Each `EnvironmentFile=` reference triggers a **second scan pass** that discovers the referenced file as its own `Configuration` entity, owned by the referencing unit's Service entity — analyzed generically (never re-dispatched through the systemd parser, never expanded further).
  - **nginx** (§18): `listen`, `server_name`, `root`, `proxy_pass`, `include` directives (indexed per directive kind), plus `upstream <name> { ... }` block names.
  - **Apache/httpd** (§19): `<VirtualHost ...>` argument strings, `Listen`, `ServerName`, `DocumentRoot`, `ProxyPass`, `Include`.
  - **PHP** (§20): referenced `extension=`/`zend_extension=` module names.
  - **MySQL/MariaDB** (§21): `datadir`, `socket`, `port`, `bind-address` (first occurrence wins, matching MySQL's own override semantics closely enough for discovery).
  - **PostgreSQL** (§22): `port`, `listen_addresses`, `data_directory`, `include` (quoted values unwrapped, `#` comments ignored).
  - **SSH** (§24): `Port`, `ListenAddress`, `Include`, `HostKey` (indexed — multiple `HostKey` lines are common) — **never reads private key file content**, only records the referenced path string.
  - **Docker**: no dedicated parser — `/etc/docker/daemon.json` is plain JSON, fully covered by the generic JSON structural validator/content analyzer alone.
- **Generic Cross-Format Analysis** (`ConfigurationContentAnalyzer`, shared with Windows, extended in Phase 6E): secrets (via `ISecretRedactor`), HTTP/HTTPS/LDAP/LDAPS endpoints, database connection-string references, bare `$VAR`/braced `${VAR}`/default-valued `${VAR:-default}` environment references (name captured, default text never captured), Unix domain socket paths (`/run|/var/run|/tmp/*.sock`), and NFS (`server:/export/path`)/CIFS (`//server/share`) network-storage references — all run on every file regardless of technology.
- **Entities Produced**: `Configuration` (existing Phase 1 entity, unchanged) — no `LinuxConfiguration` type introduced. `Path`, `Format`, `Evidence` (file path + `ScanRoot`/`Source`, never full content), `OwnerEntityId` (set when the scan root came from a specific Service/ScheduledTask; `Systemd`-well-known-root files and static-technology-root files carry no owner), and `Metadata` (`ParseStatus`, `ScanRootPath`, `ScanRootSource`, `IsSymlink` when applicable, per-technology facts prefixed `{Source}.{Key}` and redacted, plus the generic `Endpoint{i}.*`/`Database{i}.*`/`NetworkStorage{i}.*`/`UnixSocket{i}` metadata).
- **Secret Handling**: every technology fact and every generic-analysis value passes through `ISecretRedactor` before ever reaching metadata — verified end-to-end by a test scanning a realistic multi-file fixture (nginx comment, MySQL comment, and a systemd `ExecStart` argument all carrying the same secret marker) and asserting it never appears in any entity's metadata or evidence.
- **Symlink Handling** (§28): `ConfigurationFileRow.IsSymlink` (from `IFileSystemReader.GetFileInfo().IsReparsePoint`) is recorded as metadata when true — the observed path is what's read; no separate symlink-target resolution is ever attempted, and no root is ever escaped via a symlink (trivially true, since no such resolution code exists at all).
- **Permission Handling**: a single inaccessible root/file degrades the scanner to `PartiallySupported` with a recorded `DiscoveryError` (not `AccessDenied` at the scanner level, since other roots may still succeed) — a root simply not existing is normal and silently skipped, never an error.
- **Security Considerations**: `LinuxConfigurationScanner` has **no** `IProcessRunner`/`IKubernetesProvider`/`IContainerRuntimeProvider` dependency at all — it is structurally, not merely behaviorally, incapable of running `nginx -t`, `apachectl`, `php`, `mysql`, `psql`, touching the Docker socket, or calling the Kubernetes API. Verified by a reflection-based test asserting its constructor's dependency graph contains none of those types.
- **Known Limitations**: application-root derivation only recognizes the `bin`/`sbin` convention (documented above); per-technology parsers are conservative regex extractors, not full grammar parsers (an unusual or heavily macro-driven nginx/Apache configuration may not have every directive captured — the generic analysis still runs regardless); no real-machine validation was performed on this Windows development host.
- **Tests**: `LinuxScanRootCollectorTests` (11), `LinuxConfigurationTechnologyAnalyzerTests` (10), `LinuxConfigurationScannerBuildEntityTests` (8), `LinuxConfigurationScannerScanAsyncTests` (8 — including the systemd-EnvironmentFile second-pass discovery test), `LinuxConfigurationNegativeSecurityTests` (3). Plus `ConfigurationContentAnalyzerLinuxExtensionsTests` (10, in `ServerSleuth.Infrastructure.Tests`) covering the shared analyzer's new Linux-oriented patterns, and one additional `ServiceCollectionExtensionsTests` case confirming the systemd/cron scanners resolve identically as concrete types and via `IDiscoveryScanner`.

## Linux Native Dependency Scanner (`linux-native-dependency-scanner`, Phase 6F)

- **Purpose**: Discover ELF native binary dependencies (DT_NEEDED shared libraries) from already-discovered executable evidence — the Linux counterpart to Windows's PE/DLL import analysis (Phase 4E-2), and the phase that resolves the previously documented "per-runtime architecture detection remains out of scope" limitation.
- **Supported Platforms**: Linux.
- **Architecture**: `ILinuxElfParser`→`ElfParser` (pure ELF parsing) is kept fully separate from `ILibraryResolver`→`LinuxLibraryResolver` (dependency resolution) and from `LinuxNativeDependencyScanner` (orchestration/entity creation) — no single class does all three. Re-runs `LinuxProcessScanner`, `LinuxSystemdServiceScanner`, `LinuxScheduledTaskScanner`, and `LinuxRuntimeDiscoveryScanner` directly (all four registered as their own concrete types in DI, extending the pattern Phase 6E introduced) purely to obtain executable paths — never a filesystem-wide ELF search.
- **Input Scope**: only paths already present on discovered entities — `Process.Path`, `Service.ExecutablePath`, `ScheduledTask.Action` (already-resolved rooted paths only), and `Runtime.Path`/`Sdk.Path` (the base `DiscoveryEntity.Path`, which the Phase 6B runtime detectors already populate). Every referencing entity's ID is preserved as an owner; the same path referenced by multiple entities is analyzed exactly once.
- **ELF Parsing** (`ElfParser`, hand-written, minimal — magic/EI_CLASS/EI_DATA/e_machine/program headers/dynamic section/DT_NEEDED/DT_RPATH/DT_RUNPATH only; no disassembler, no DWARF, no symbol-table analysis):
  - **Architecture Detection**: ELF32/ELF64 via EI_CLASS; machine mapping covers x86/i386 (EM_386→X86), x86_64 (EM_X86_64→X64), ARM (EM_ARM→Arm), AArch64 (EM_AARCH64→Arm64), and RISC-V (EM_RISCV→RiscV, a new `EntityArchitecture` member added this phase). An unrecognized `e_machine` value maps to `Unknown` but the raw value (`EM_<n>`) is still preserved as metadata — never silently discarded, never inferred from filename/directory/runtime family/CPU name/package name.
  - **Endianness**: only little-endian (EI_DATA=1) is parsed past the identification header. Big-endian (EI_DATA=2) is recognized and returns `ElfParseStatus.UnsupportedEndian` with a diagnostic — the parser deliberately never decodes a single further multi-byte field for big-endian input, since doing so would require byte-swapping logic this parser doesn't implement; never guessed at.
  - **DT_NEEDED/DT_RPATH/DT_RUNPATH**: extracted by locating the PT_DYNAMIC program header, translating DT_STRTAB's virtual address to a file offset via the PT_LOAD segments, then reading null-terminated strings from that string table at each dynamic entry's recorded offset. DT_RPATH/DT_RUNPATH are split on `:` and kept as two independent lists — never merged, since the real dynamic loader's search-order semantics differ between the two.
  - **Malformed/truncated input**: every failure path (missing magic, file shorter than the ELF/program headers, a corrupted `e_phoff`/`e_phnum` pointing past end-of-file, an internally inconsistent offset/size anywhere in the dynamic section) is caught and classified — `NotAnElf`/`Truncated`/`MalformedElf`/`PartiallyParsed` — never an unhandled exception. A binary with no PT_DYNAMIC segment at all (a statically linked binary) is a completely valid `Parsed` result with zero dependencies, not an error.
- **Dependency Resolution** (`LinuxLibraryResolver`, fixed and documented five-tier order — skill.md §10):
  1. Explicit RPATH entries (file order, first existing candidate wins)
  2. RUNPATH entries (file order)
  3. Already-discovered binary paths sharing the exact requested filename — `Ambiguous` (with every candidate recorded) if more than one distinct path matches, since there is no principled way to prefer one
  4. A fixed, documented list of well-known Linux library directories (`/lib`, `/lib64`, `/usr/lib`, `/usr/lib64`, and the Debian/Ubuntu x86_64/aarch64 multiarch triplet directories)
  5. The optional `ldconfig` cache (tier 5), if the provider is available
  - **`$ORIGIN` expansion**: the one RPATH/RUNPATH token this resolver substitutes, replaced with the importing binary's own directory — a legitimate, bounded, deterministic expansion mirroring real dynamic-loader semantics. `$LIB`/`$PLATFORM` are not substituted (documented limitation).
  - **Path security**: every candidate path is lexically normalized (`.`/`..` segments collapsed) before any filesystem check — a `..`-laden RPATH entry can never walk above `/`, and no filesystem access occurs during normalization itself (no symlinks followed, no directory enumerated). Only the exact candidate path is ever checked for existence — never a directory listing.
  - **Missing/unresolved dependencies are never fabricated**: a DT_NEEDED name that resolves against nothing becomes `LibraryResolutionStatus.NotFound`, preserved on the entity as an auditable, unresolved reference — no `/usr/lib/<name>` path is ever invented, and no placeholder `Dll` entity is created just to complete a graph.
  - **AccessDenied is distinguished from NotFound**: a candidate check that hits a real permission wall (rather than simply not existing) is tracked separately, so a resolution that fails only because every candidate was inaccessible reports `AccessDenied`, not a false `NotFound`.
- **ldconfig** (`LdconfigProvider`, optional last-resort tier): the only command ever invoked is `ldconfig -p` — never bare `ldconfig` (which can rebuild the cache), never any write operation. Unavailability (missing executable, non-zero exit, unparseable output) yields an empty cache and never fails the scan. **`ldd` was deliberately not implemented** — DT_NEEDED parsing is the sole authoritative dependency source, per the phase's explicit preference.
- **Entities Produced**: `Dll` (existing Phase 1 entity, unchanged, `Type = "NativeBinary"`) — no `LinuxBinary`/`ElfBinary` type introduced. `Architecture` (the shared `DiscoveryEntity`/`Dll` field Windows's PE analysis also populates) carries the ELF-derived value; `ReferencedByEntityIds` carries every owning Process/Service/ScheduledTask/Runtime/Sdk entity ID. ELF class/endianness/machine/RPATH/RUNPATH/diagnostic and every resolved dependency's name/status/resolved-path/source/candidates are recorded as metadata — never raw binary content.
- **Dependency Evidence**: every DT_NEEDED entry gets its own `EvidenceType.BinaryImport` evidence record (`Location = "ELF dynamic section"`, `Detail = "DT_NEEDED=<name>"`) — a new `EvidenceType` member added this phase — giving Phase 5A's existing `Binary → IMPORTS → Binary` correlation rule enough information to operate later, without this scanner invoking `CorrelationEngine` itself or modifying any Phase 5A rule.
- **Permission Handling**: an inaccessible binary (`AccessDenied` on either the file-info check or the byte read) degrades the scanner to `PartiallySupported` with a recorded `DiscoveryError`, without discarding the binaries that were readable; a binary simply not found at its recorded path is `NotFound`, not an error.
- **Container/Kubernetes Boundary**: this scanner has no `IContainerRuntimeProvider`/`IKubernetesProvider`/`IProcessRunner`-beyond-`ldconfig` dependency anywhere in its graph — it cannot invoke `docker exec`/`podman exec`/`kubectl exec`, cannot inspect `/var/lib/docker`/`/var/lib/containers`, and cannot access a Pod filesystem, because no code path exists that would let it try.
- **Security Considerations**: no binary is ever executed (`Process.Start`, `dlopen`/`LoadLibrary`-equivalent dynamic loading, and shell execution are all absent from this scanner's entire dependency graph); the analyzed binary itself is read only as bytes via `IFileSystemReader.ReadBytesAsync`, never invoked. Verified by a dedicated negative-security test asserting the *only* process ever started across a full discovery run is `ldconfig -p`.
- **Performance**: bounded to already-discovered paths only, each parsed exactly once (deduplicated by exact, case-sensitive path); a 200MB per-file cap bounds memory usage against a pathological input; library resolution only ever checks one exact candidate path per tier/entry, never enumerating a directory's contents.
- **Known Limitations**: only `$ORIGIN` is expanded (not `$LIB`/`$PLATFORM`); the well-known library directory list covers common x86_64/aarch64 multiarch triplets only; `ldd` was deliberately not implemented; no real-machine validation performed on this Windows development host.
- **Tests**: `ElfParserTests` (19, against a hand-written `SyntheticElfBuilder` producing real, structurally valid synthetic ELF32/ELF64 fixtures — never real machine binaries as the only source), `LinuxLibraryResolverTests` (12), `LdconfigProviderTests` (4), `LinuxNativeDependencyScannerBuildEntityTests` (10), `LinuxNativeDependencyScannerScanAsyncTests` (10), `LinuxNativeDependencyNegativeSecurityTests` (3 — the only invoked process is `ldconfig -p`, no other execution-capable dependency exists anywhere in the graph, the analyzed binary is never executed).

# Infrastructure Abstractions (Phase 2)

---

## IProcessRunner / ProcessRunner

- **Purpose**: Execute an external command and capture its result without ever building a shell command string, so scanners cannot introduce command injection via discovered/derived values.
- **Supported Platforms**: Both (uses `System.Diagnostics.Process`, cross-platform in .NET).
- **Data Sources**: Whatever executable/arguments the caller supplies (e.g. future `dotnet --list-runtimes`, `systemctl show`).
- **Permissions**: Runs with the calling process's privileges; no elevation requested or assumed.
- **Entities Produced**: None directly — it's a primitive used by scanners in later phases.
- **Evidence Produced**: None directly — callers wrap its `ProcessResult` (stdout/stderr/exit code) into `EvidenceRecord { Type = Command }`.
- **Known Limitations**: Command discovery availability ("is `dotnet` on PATH") is the caller's concern — `ProcessRunner` reports `OperationStatus.NotFound` on a missing executable rather than pre-checking; only Windows fixtures (`cmd.exe`, `ping`) are currently exercised in tests since the dev/CI environment is Windows-only — Linux fixtures (`sh`, `sleep`) are deferred to Phase 6 when Linux scanners land.
- **Security Considerations**: Launches via `ProcessStartInfo.ArgumentList` (each argument passed as a discrete array element to the OS, never concatenated into one command line string) — this is what prevents shell metacharacters in an argument from being reinterpreted. Kills the entire process tree on timeout or cancellation to avoid orphaned children.
- **Tests**: `test/ServerSleuth.Infrastructure.Tests/Process/ProcessRunnerTests.cs` — successful run, non-zero exit, stdout capture, stderr capture, invalid-argument non-zero exit, timeout, cancellation, executable-not-found.

## IFileSystemReader / FileSystemReader

- **Purpose**: Read-only filesystem access (existence checks, text/byte reads, enumeration) with permission/IO failures surfaced as data, not exceptions that would crash a scan.
- **Supported Platforms**: Both.
- **Data Sources**: Local filesystem paths supplied by the caller.
- **Permissions**: Runs with the calling process's privileges; `AccessDenied` is a normal, expected outcome, not a bug.
- **Entities Produced**: None directly — feeds `File`, `Configuration`, and other entities in later phases.
- **Evidence Produced**: None directly — callers wrap results into `EvidenceRecord { Type = FileSystem | ConfigurationFile }`.
- **Known Limitations**: No filesystem-wide walking helper is provided by design (skill.md §36 — "do not scan the entire filesystem indiscriminately"); callers must pass targeted directories.
- **Security Considerations**: Never executes discovered files; text/byte reads are read-only (`FileMode.Open` semantics via `File.ReadAllText/Bytes`, no write access requested).
- **Tests**: `test/ServerSleuth.Infrastructure.Tests/FileSystem/FileSystemReaderTests.cs` — exists checks, text/byte reads, missing file → `NotFound`, directory-as-file read → `AccessDenied`, locked file → `IoError`, file/directory enumeration including missing-directory case.

## IPortInspector

- **Purpose**: Cross-platform contract for enumerating listening/active network endpoints, so a future port scanner is not written directly against a platform-specific API.
- **Supported Platforms**: Both (interface only in Phase 2).
- **Data Sources**: None yet — no concrete implementation exists. Windows implementation (Phase 3) will use platform APIs (e.g. `IPGlobalProperties`/native calls); Linux implementation (Phase 6) will parse `/proc/net/tcp[6]`, `/proc/net/udp[6]` or use `ss`/`netstat`.
- **Permissions**: N/A until implemented.
- **Entities Produced**: Will feed `Port` entities once implemented.
- **Evidence Produced**: Will produce `EvidenceRecord { Type = NetworkSocket }` once implemented.
- **Known Limitations**: Deliberately unimplemented in Phase 2 per skill.md's phase ordering — only the interface and `NetworkEndpoint` DTO exist, exercised in tests via `FakePortInspector`. Not registered in `AddServerSleuthInfrastructure()` since there is nothing to bind it to yet.
- **Security Considerations**: N/A until implemented — future implementation must not attempt to identify a service from the port number alone (skill.md §13 — the owning process is authoritative).
- **Tests**: `test/ServerSleuth.Infrastructure.Tests/Networking/PortInspectorContractTests.cs` — contract-only, against `FakePortInspector` (empty result, multiple endpoints spanning TCP/UDP and IPv4/IPv6, process-id correlation).

## ISecretRedactor / SecretRedactor

- **Purpose**: Detect and redact secret-shaped values (passwords, connection strings, API keys, tokens, private keys) before they can enter a `DiscoveryEntity`, `EvidenceRecord`, or log line.
- **Supported Platforms**: Both (pure string/regex logic, no OS dependency).
- **Data Sources**: N/A — operates on strings passed to it by callers (config file contents, environment variable values, command output, etc.).
- **Permissions**: N/A.
- **Entities Produced**: None directly — used by every future scanner/serializer that might see secret-shaped text before it becomes `EvidenceRecord.Detail`, `Configuration.SecretDetected`, or a log line.
- **Evidence Produced**: None directly.
- **Known Limitations**: Rule set covers the patterns explicitly named in skill.md §24 (`Password=`, `Pwd=`, `UserPassword=`, `ConnectionString=`, `API_KEY=`, `TOKEN=`, `SECRET=`, `PRIVATE_KEY=`) plus PEM private key blocks, JWTs, and `Bearer` tokens — it is not an exhaustive secret scanner (e.g. cloud-provider-specific credential shapes like AWS access keys are not yet covered; add as new `SecretRedactionRule` entries when needed, per skill.md §38 extensibility). Quoted values containing internal whitespace are captured whole (including the quotes) rather than being parsed further.
- **Security Considerations**: This is the single point every scanner and the logging pipeline should route text through before persisting/logging it — see skill.md §16 (never log secrets) and §24 (never write secrets into reports). Rules are anchored so a key must be immediately followed by a separator and a value to match, deliberately avoiding false positives on lookalike identifiers (`TokenType=`, `PasswordPolicy=`, `SecretQuestion=`) or prose mentioning the word "token"/"secret" — verified by explicit negative test cases.
- **Tests**: `test/ServerSleuth.Infrastructure.Tests/Security/SecretRedactorTests.cs` — all listed key patterns, case-insensitivity, separator spacing variants, multiple secrets in one string, key-name preservation after redaction, PEM block redaction, Bearer token redaction, false-positive avoidance (6 lookalike cases including an already-redacted string), and a plain-configuration negative case.

## AddServerSleuthInfrastructure() (DI registration)

- **Purpose**: Single composition point registering the concrete Infrastructure implementations, so Windows/Linux scanner projects and the CLI don't each hand-wire `ProcessRunner`/`FileSystemReader`/`SecretRedactor`.
- **Registers**: `IProcessRunner`→`ProcessRunner`, `IFileSystemReader`→`FileSystemReader`, `ISecretRedactor`→`SecretRedactor`, all singleton.
- **Does not register**: `IPortInspector` (no implementation yet, see above).
- **Tests**: Covered indirectly — each concrete type is unit-tested directly; the DI wiring itself has no behavior to test beyond "does it resolve," which will be validated end-to-end once the CLI composition root exists (Phase 9).

## Discovery Scanner Registry (`IDiscoveryScannerRegistry`/`DiscoveryScannerRegistry`)

- **Purpose**: A deterministic, in-process catalog of every registered `IDiscoveryScanner` — the foundation of "prove ServerSleuth operates as one cross-platform discovery system" (skill.md (Phase 6G) §1-3).
- **Location**: `ServerSleuth.Core/Orchestration/` — deliberately in Core, not Infrastructure/Windows/Linux, since it must never reference either platform project. Platform availability is determined entirely by which composition-root method (`AddServerSleuthWindows()`/`AddServerSleuthLinux()`) populated the DI container's `IDiscoveryScanner` registrations before the registry itself resolves them — there is no `if (OperatingSystem.IsWindows())` anywhere in this type.
- **Determinism**: scanners are sorted once, at construction, by `Id` (ordinal string comparison) — never left in DI-container registration order or dictionary/hash-set enumeration order, either of which can vary between processes or .NET versions. Verified by a test constructing the registry twice from the same (deliberately shuffled) input and asserting identical ordering both times.
- **Not a plugin system**: no dynamic assembly loading, no reflection-based scanner discovery — every scanner is registered explicitly by a composition-root call, exactly as before this phase.
- **Tests**: `DiscoveryScannerRegistryTests` (3 — deterministic ordering regardless of construction order, ordering stability across repeated construction, empty registration produces an empty registry without throwing).

## Discovery Engine (`IDiscoveryEngine`/`DiscoveryEngine`)

- **Purpose**: Runs every scanner in a registry once and produces one deterministic `AggregateDiscoveryResult` (skill.md (Phase 6G) §2, §7).
- **Fault isolation**: if a scanner throws an unhandled exception (which a well-behaved scanner should never do, since every existing scanner already catches its own expected failure modes into a `DiscoveryResult`/`DiscoveryError`, but this engine defends against it regardless), that one scanner's result is replaced with a synthetic `ScannerStatus.Failed` result carrying a `DiscoveryError`, an engine-level diagnostic is recorded, and every other scanner still runs to completion — the whole orchestration run is never aborted by one scanner's misbehavior.
- **Never silently discards a failure**: `AccessDenied`/`PartiallySupported`/`Failed` scanner results all remain fully visible in `ScannerResults`/`ScannerStatuses` — an aggregate "everything succeeded" summary is never fabricated by omission.
- **Duplicate handling**: the engine performs zero merging of any kind — `Entities` is simply every scanner's own entities concatenated in registry order. Two different scanners producing entities that a human might consider "the same logical thing" (different IDs, same real-world referent) are both preserved untouched; deciding whether/how to correlate them is `ServerSleuth.Analysis`'s job (Phase 5), never the orchestrator's — verified by a dedicated test.
- **Tests**: `DiscoveryEngineTests` (8 — multi-scanner aggregation, a `PartiallySupported` scanner never affecting another scanner's own status, an `AccessDenied` scanner remaining fully visible, one scanner throwing degrades only that scanner to `Failed` while others still run, duplicate-observation preservation, deterministic ordering across two full runs with scanners constructed out-of-order, empty-registry handling, cancellation propagation).

## AddServerSleuthDiscoveryEngine() (DI registration)

- **Purpose**: Registers `IDiscoveryScannerRegistry`→`DiscoveryScannerRegistry` and `IDiscoveryEngine`→`DiscoveryEngine`. Kept as its own extension method (in `ServerSleuth.Infrastructure.DependencyInjection`, alongside `AddServerSleuthInfrastructure()`) rather than folded into `AddServerSleuthInfrastructure()`, because it must be called *after* whichever platform registration methods (`AddServerSleuthWindows()`/`AddServerSleuthLinux()`) the composition root uses, so the registry actually has scanners registered for `IEnumerable<IDiscoveryScanner>` to enumerate.
- **Tests**: `ServiceCollectionExtensionsTests` (2, in `ServerSleuth.Infrastructure.Tests/DependencyInjection/`) — registry/engine resolve to the expected concrete types; an empty composition (no platform registered) produces an empty registry without throwing.

## Cross-Platform Integration Tests (`ServerSleuth.Integration.Tests`, new project)

- **Purpose**: The one test project that references both `ServerSleuth.Windows` and `ServerSleuth.Linux` together (target framework `net8.0-windows`, so it can reference the Windows-only-TFM project) — proving the composition and shared-vocabulary goals of Phase 6G that no single existing platform-specific test project could prove alone.
- **`CrossPlatformCompositionTests`** (6): composing `AddServerSleuthInfrastructure()+AddServerSleuthWindows()+AddServerSleuthLinux()+AddServerSleuthDiscoveryEngine()` in one `ServiceCollection` produces a registry whose scanner count is exactly the sum of each platform's own independently-measured scanner count (never hard-coded as a literal number, to avoid silent staleness as either platform adds scanners); no duplicate scanner IDs; every `windows-*`-prefixed scanner reports `PlatformSupport.Windows` and every `linux-*`-prefixed scanner reports `PlatformSupport.Linux` (never hard-coded elsewhere); deterministic Id-ordinal ordering across the mixed set; `IDiscoveryEngine` resolves successfully from the composed container; and registering only one platform never pulls in the other's scanners.
- **`CrossPlatformAnalysisFixtureTests`** (8): a synthetic fixture containing genuinely mixed Windows-shaped (IIS `WebSite`/`Application`, Windows `Service`, `Configuration`, `Runtime`, managed `Dll`, `Certificate`) and Linux-shaped (systemd `Service`, `Configuration`, `Runtime`, native ELF `Dll`, `ExternalDependency`) entities constructed directly (not via real scanners, since the point is the shared vocabulary and the Analysis engines, not re-testing scanner discovery logic) — fed through `CorrelationEngine`→`ApplicationBoundaryEngine`→`DependencyExpansionEngine`→`GraphValidator` in one run. Asserts: the pipeline never throws on mixed-platform input; every graph node traces back to an original fixture entity (nothing fabricated); no dangling edges (every edge's source/target is a real entity ID); no entity carries positive confidence without at least one evidence record; zero `Error`-severity validation findings; deterministic results across two independent runs of the same fixture shape; and — the vocabulary proof itself — both platforms' `Service` entities are the same `Core.Models.Service` type (distinguished only by `Source`, never a subtype) and both platforms' binaries are the same `Core.Models.Dll` type (distinguished only by `Type` — `"ManagedDll"` vs `"NativeBinary"` — never a subtype).
- **Real Linux confirmation**: this entire project (all 14 tests) was executed on the real WSL Ubuntu 24.04 LTS instance used for Phase 6G's Real Linux Validation (see PROGRESS.md) and passed identically to the Windows run — direct proof that the cross-platform composition and the mixed-platform Analysis pipeline both function correctly regardless of which OS is running them.

## Remote Discovery over SSH (Phase 10D-2)

- **Purpose**: Lets every Linux scanner/provider below run against a remote Linux target over SSH, without changing the scanner itself — see `ARCHITECTURE.md`'s Phase 10D-2 addendum for the full transport design (`SshRemoteTargetTransport`/`SshProcessRunner`/`SshFileSystemReader`/`ISshSession`/`SshNetSession`, host-key verification, credential boundary, command-injection defenses).
- **How a scanner becomes remote-capable**: automatically, if (and only if) it depends exclusively on `IProcessRunner`/`IFileSystemReader` (never a direct BCL/OS API call) — the CLI composition root swaps which implementation of those two interfaces the whole DI container resolves, based on `--target`, with zero change to the scanner/provider itself.
- **Already remote-capable (no code change needed)**: `linux-os-scanner`, `linux-process-scanner` (via `LinuxProcProvider`, which Phase 10D-2 additionally fixed to resolve `/proc/<pid>/exe` through `IFileSystemReader.ReadLinkTarget` instead of the local disk directly), `linux-port-scanner`, `linux-systemd-service-scanner`, `linux-package-scanner`, `linux-runtime-discovery-scanner`, `linux-scheduled-task-scanner` (cron; filesystem-only, no process dependency at all), `linux-container-scanner`, `linux-kubernetes-scanner`, `linux-configuration-scanner`, `linux-native-dependency-scanner`. This is every registered Linux scanner — Linux discovery's entire operation surface was already representable by the existing `IProcessRunner`/`IFileSystemReader` contracts before this phase touched anything.
- **Read-only command vocabulary preserved**: every process-issuing Linux provider was verified (source-scan, `ReadOnlyCommandVocabularyTests`) to issue only its existing read-only subcommands — `systemctl show`/`list-units` (never `start`/`stop`/`restart`/`enable`/`disable`/`reload`/`mask`/`kill`), `dpkg-query -W`/`rpm -qa`/`apk info -v` (never `install`/`remove`/`upgrade`/`add`/`del`), `docker`/`podman ps`/`inspect`/`images`/`volume ls`/`network ls`/`network inspect` (never `exec`/`run`/`start`/`stop`/`rm`/`pull`/`push`/`build`), `kubectl get ...` (never `exec`/`apply`/`create`/`delete`/`patch`/`edit`/`rollout`/`port-forward`), `ldconfig -p`. No provider was modified to add or change a command — this test locks in what was already true.
- **CLI usage**: `serversleuth scan --target <host> --ssh-user <user> --ssh-key <private-key-path> --ssh-host-fingerprint <sha256> [--ssh-port <port>] [--ssh-key-passphrase-env <VAR>]`. `--target local`/omitted is unchanged.
- **Not yet remote-capable**: no Windows scanner (Registry/WMI/COM/`ServiceController`/IIS/Task Scheduler/Certificates all call Windows-only BCL/COM APIs directly, never through `IProcessRunner`/`IFileSystemReader`) — Windows/WinRM remote scanning remains entirely unimplemented.

## Windows Remote Capability Model (Phase 10D-3A)

- **Purpose**: a structured, typed DATA model (never a raw command/PowerShell/WQL string) representing every remote operation a future WinRM transport would need to serve Windows discovery — see `ARCHITECTURE.md`'s Phase 10D-3A addendum for the full design rationale and vocabulary-sizing decisions. This phase implements the MODEL only — no WinRM/PowerShell Remoting/WS-Man network call exists anywhere; `WindowsRemoteCapabilityFactory.Create(ScanTarget)` always throws `NotSupportedException`.
- **Vocabulary** (`WindowsRemoteOperationKind`, 5 members, in `src/ServerSleuth.Windows/Remote/`): `RegistryQuery`, `WmiQuery`, `IisQuery`, `TaskSchedulerQuery`, `CertificateQuery`. `ServiceQuery` was folded into `WmiQuery` (`Win32_Service` is a WMI class); `ComRegistryQuery` was folded into `RegistryQuery` (COM registration is already read entirely through `IWindowsRegistryReader` today, via `ComClsidReader`). A SEPARATE enum from the cross-platform `RemoteOperationKind` (Phase 10D-1/10D-2) — these are Windows-domain concepts with no generic ProcessQuery/FileRead/DirectoryQuery shape.
- **Registry** (`src/ServerSleuth.Windows/Registry/`): `WindowsRegistryQuery`/`WindowsRegistryQueryResult`/`IWindowsRemoteRegistryOperations` — one request shape (`IncludeSubKeys`/`IncludeValues`/`ValueNames`) collapsing `IWindowsRegistryReader`'s three existing methods, reusing the existing `Microsoft.Win32.RegistryHive`/`RegistryView` BCL enums. Read-only by construction — no write/delete/rename/ACL field exists anywhere on the type.
- **WMI** (`src/ServerSleuth.Windows/Wmi/`): `WindowsWmiQuery`/`WmiFilterClause`/`WmiComparisonOperator`/`IWindowsRemoteWmiOperations` — structured `Namespace`/`ClassName`/`Properties`(select list)/`Filters` (a closed `Equals`/`NotEquals` comparison, ANDed), never raw WQL, never a method-invocation field. **Disclosed gap**: cannot represent `ProcessWmiProvider.TryGetOwner`'s `Win32_Process.GetOwner()` method invocation — `ProcessWmiInfo.OwnerDomain`/`OwnerUser` has no remote-capability equivalent in this model (no WMI-method-execution capability exists at all, a hard security requirement).
- **IIS** (`src/ServerSleuth.Windows/IIS/IWindowsRemoteIisOperations.cs`): parameterless `GetSnapshot()` returning the SAME `IisSnapshot` `IIisConfigurationProvider` already returns. No mutation method of any kind.
- **Task Scheduler** (`src/ServerSleuth.Windows/ScheduledTasks/IWindowsRemoteTaskSchedulerOperations.cs`): parameterless `GetSnapshot()` returning the SAME `ScheduledTaskRow` list `ITaskSchedulerProvider` already returns. No `Run`/`Delete`/`Register`/`Enable`/`Disable` method — never executes a discovered task's own action.
- **Certificates** (`src/ServerSleuth.Windows/Certificates/IWindowsRemoteCertificateOperations.cs`): `Query(CertificateStoreSource)` returning the SAME `CertificateRow` list `ICertificateStoreProvider` already returns. `CertificateRow.HasPrivateKey` remains a boolean flag only — structurally no member anywhere can return private-key bytes.
- **Composition** (`src/ServerSleuth.Windows/Remote/`): `IWindowsRemoteCapabilities` bundles `Target`+5 narrow interfaces (mirrors `ITargetTransport`'s Target/ProcessRunner/FileSystemReader shape); `WindowsRemoteOperationResult<T>` is the shared result envelope (reuses `OperationStatus`, no second status enum); `WindowsRemoteCapabilityFactory.Create` is the always-throwing seam a future WinRM implementation fills in, mirroring `RemoteTargetTransportFactory.Create`'s pre-Phase-10D-2 shape.
- **Not yet remote-capable**: every Windows scanner remains unchanged and local-only — this phase adds no transport, so nothing actually became remotely scannable. `IProcessEnumerator`/`ProcessEnumerator` also has a disclosed gap (hard-codes local `System.Diagnostics.Process.GetProcesses()`, bypassing every injectable abstraction) — not fixed in this phase since nothing consumes it remotely yet.
- **Tests**: 36 (`ServerSleuth.Windows.Tests/Remote/WindowsRemoteCapabilityModelTests` + `WindowsRemoteCapabilityArchitectureTests`), all against a test-only `FakeWindowsRemoteCapabilities` recording double — zero live Windows remote host required. As of Phase 10D-3B, exactly one production implementation of `IWindowsRemoteCapabilities` exists (`WinRmWindowsRemoteCapabilities`) — see below.

## Windows Remote Discovery over WinRM (Phase 10D-3B)

- **Purpose**: fills Phase 10D-3A's capability model with a REAL transport — `Microsoft.Management.Infrastructure` (the native CIM/WS-Man client library PowerShell's own CIM cmdlets use; no PowerShell script engine, no arbitrary command surface). See `ARCHITECTURE.md`'s Phase 10D-3B addendum for the full design.
- **How a Windows scanner becomes remote-capable**: automatically, for the SAME nine interfaces Phase 10D-2 established the pattern for — if a scanner/provider depends only on `IWindowsRegistryReader`/`IProcessWmiProvider`/`IProcessEnumerator`/`INetworkTableProvider`/`IProcessNameResolver`/`IServiceEnumerator`/`IIisConfigurationProvider`/`ITaskSchedulerProvider`/`ICertificateStoreProvider` (never a direct registry/WMI/COM/filesystem API call), the CLI composition root swaps which implementation of those interfaces the DI container resolves, based on `--target`, with zero change to the scanner/provider itself.
- **Already remote-capable (no code change needed)**: `windows-process-scanner`, `windows-port-scanner`, `windows-service-scanner` (service state via `Win32_Service`; registry detail via `ServiceRegistryDetailReader`, itself already routed through `IWindowsRegistryReader`), `windows-installed-software-scanner`, `windows-iis-scanner` (degrades to `NotInstalled` remotely — disclosed gap, not fabricated), `windows-com-scanner` (COM registration is already registry-only), `windows-scheduled-task-scanner` (degrades to `Failed` remotely — disclosed gap), `windows-certificate-scanner` (degrades to `NotInstalled` remotely — disclosed gap).
- **Remote-only implementations**: `WinRmWindowsRegistryReader`/`WinRmRegistryOperations` (registry reads via `StdRegProv`'s read-only WMI methods — `EnumKey`/`EnumValues`/`Get*Value`; `Registry32` unsupported, disclosed), `WinRmWmiOperations` (structured `SELECT...WHERE...` WQL, allow-listed to `Win32_Process`/`Win32_Service`/`MSFT_NetTCPConnection`/`MSFT_NetUDPEndpoint`), `WinRmProcessWmiProvider`/`WinRmProcessEnumerator`/`WinRmNetworkTableProvider`/`WinRmProcessNameResolver`/`WinRmServiceEnumerator` (all WMI-backed adapters satisfying the pre-existing local interfaces).
- **NOT remote-capable — excluded outright, not degraded (skill.md §19, §21)**: `windows-os-scanner` (reads local `Environment.*`, no remote bridge), `runtime-discovery-scanner`/`windows-configuration-scanner`/`windows-binary-discovery-scanner` (all need `IProcessRunner`/`IFileSystemReader`, no WS-Man-reachable non-PowerShell bridge exists for either). None of these four scanners are registered at all for a remote Windows target — proven by a dedicated composition test, never a silent local-fallback risk.
- **Disclosed capability gaps, honestly reported, never fabricated**: `Win32_Process.GetOwner()` (structurally representable — on the WMI method allow-list — but never invoked from the bulk process path, to avoid an N+1 remote call per scan; `ProcessWmiInfo.OwnerDomain`/`OwnerUser` are always `null` remotely). IIS (`root\WebAdministration`'s schema was never verified against a real host with the provider installed). Task Scheduler (no WMI provider for Task Scheduler 2.0 exists). Certificates (local-only `X509Store`, no safe remote alternative attempted).
- **CLI usage**: `serversleuth scan --target <host> --winrm-user <user> --winrm-password-env <VAR> [--winrm-domain <domain>] [--winrm-port <port>] [--winrm-no-ssl] [--winrm-auth negotiate|kerberos|credssp]`. TLS (`--winrm-no-ssl` omitted) is the default and fails closed — certificate/CA/CN/revocation checks are always enabled when TLS is used, with no bypass flag anywhere.
- **Platform-of-origin limitation**: a Windows/WinRM remote scan can only be initiated from a Windows-hosted `serversleuth` binary (`net8.0-windows`) — the plain `net8.0` (Linux-hosted) build has no reference to `ServerSleuth.Windows` at all.
- **Tests**: 31 new (`WinRmTransportSecurityTests` 18/Windows.Tests, `WindowsRemoteCompositionTests` 6/Cli.Tests, `ScanCommandWindowsRemoteOptionTests` 7/Cli.Tests), all against `FakeCimSession` — zero live WinRM host required for the deterministic suite. Real-network-stack verification (missing password env var, closed-port connection failure) performed against the actual dev host — see `PROGRESS.md`.
