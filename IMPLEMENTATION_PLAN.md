## Phase 1 — Core Domain

- **Objective**: Establish the platform-agnostic domain model, evidence model, scanner contract, and result/error types that every later phase depends on. No scanning, no I/O, no OS-specific code.
- **Scope**: `ServerSleuth.Core` only, plus its test project. Explicitly excluded (per operating instructions §7): GUI, Web UI, IIS/COM/Linux/Docker scanners, risk engine, HTML report, database integration, cloud integration.
- **Projects**: `src/ServerSleuth.Core/ServerSleuth.Core.csproj`, `test/ServerSleuth.Core.Tests/ServerSleuth.Core.Tests.csproj`, root `ServerSleuth.sln`.
- **Files/Models** (`ServerSleuth.Core/Models/`, `Enums/`, `Evidence/`, `Graph/`, `Interfaces/`):
  - `DiscoveryEntity` (base) and concrete entities: `Server`, `OperatingSystem`, `Service`, `Process`, `Port`, `Application`, `Software`, `Package`, `Runtime`, `Sdk`, `Dll`, `ComComponent`, `WebSite`, `ApplicationPool`, `ScheduledTask`, `Container`, `Database`, `Certificate`, `Configuration`, `EnvironmentVariable`, `File`, `ExternalDependency`.
  - `EntityStatus` enum: `Installed | Configured | Running | Listening | Referenced | Used | Unknown`.
  - `Evidence`, `EvidenceType` enum (per §6 list), `Confidence` (value type enforcing the 0.00–1.00 range + band lookup: VeryHigh/High/Medium/Low/VeryLow).
  - `DiscoveryResult`, `DiscoveryError`, `ScannerStatus` enum (`Supported | PartiallySupported | AccessDenied | NotApplicable | NotInstalled | Failed`).
  - `PlatformSupport` enum/flags (Windows, Linux, Both).
  - `DiscoveryContext` (ScanProfile, CancellationToken, scan-root config — no mutable global state).
  - `ScanProfile` enum: `Quick | Standard | Deep | Migration`.
  - `Dependency` (edge: SourceId, TargetId, `DependencyEdgeType`, Evidence[], Confidence) and `DependencyEdgeType` enum (HOSTS, RUNS, BINDS, USES, DEPENDS_ON, LOADS, LISTENS_ON, HOSTED_BY, CONFIGURED_BY, REFERENCES, CALLS, CONNECTS_TO).
  - `DependencyGraph` (Nodes, Edges, add/query methods — no analysis logic, just structure).
  - `IDiscoveryScanner` interface.
- **Interfaces**: `IDiscoveryScanner` (Id, PlatformSupport, `ScanAsync`). No scanner registry interface yet unless needed to type-check registration — defer concrete registry implementation to Phase 2/9 per skill.md §39, but the interface it depends on (`IDiscoveryScanner`) belongs here.
- **Dependencies**: none beyond BCL. No third-party NuGet packages in Core (keep it dependency-free per §17 extensibility goals).
- **Tests** (`ServerSleuth.Core.Tests`, xUnit): domain model initialization/validation, Evidence attachment and multiplicity, Confidence band boundaries, DiscoveryResult success/failure aggregation, DiscoveryError content, ScannerStatus values, DependencyGraph node/edge add + duplicate-edge handling, entity equality/identity for dedup groundwork.
- **Acceptance Criteria**:
  - `dotnet restore`, `dotnet build`, `dotnet test` all succeed from repo root.
  - Every model above exists with XML-doc-free, nullable-enabled, small focused types (no God classes).
  - No project other than `ServerSleuth.Core`/`ServerSleuth.Core.Tests` exists yet.
  - `PROGRESS.md` and `CHANGELOG.md` updated with real build/test output, not claimed results.
- **Risks**: over-modeling fields that don't apply to every entity (spec explicitly forbids forcing inapplicable fields, §5) — mitigate by using a lean base + only-relevant-fields-per-entity, not one flat table with nullable everything.

## Phase 2 — Common Infrastructure

- **Objective**: Cross-platform technical abstractions that both Windows and Linux scanners will depend on, so scanners never call `Process.Start`/`File.ReadAllText`/raw sockets directly.
- **Scope**: `ServerSleuth.Infrastructure` (Common, FileSystem, Networking, Process) + tests. Still no scanners.
- **Projects**: `src/ServerSleuth.Infrastructure/`, `test/ServerSleuth.Infrastructure.Tests/`.
- **Interfaces/Models**: `IProcessRunner` (async, timeout + `CancellationToken`, captures stdout/stderr, never throws on nonzero exit — returns a result object), `IFileSystemReader`, `IPortInspector`, `SecretRedactor` (pattern list from §24, redact-in-place helper used by every scanner that reads text), structured logging setup (`ILogger`-based, with the `ScannerStarted/Completed/Failed/Skipped/PermissionDenied/DiscoveryCount` event names from §37 as constants, not ad hoc strings).
- **Dependencies**: `Microsoft.Extensions.Logging.Abstractions`, `Microsoft.Extensions.DependencyInjection.Abstractions`. No logging *provider* pinned yet (Cli phase wires the concrete sink).
- **Tests**: `IProcessRunner` against a real short-lived process (e.g. `cmd /c echo`/`sh -c echo` depending on OS) with timeout and cancellation behavior; `SecretRedactor` against each pattern in §24 plus negative cases (value that looks like a secret pattern but isn't, e.g. a URL containing "token" as a path segment — decide and document the false-positive tolerance); command-unavailable path returns a typed "not found" result rather than throwing.
- **Acceptance Criteria**: build/test green; `SecretRedactor` unit tests demonstrate no raw secret value ever survives redaction for every pattern in the spec.
- **Risks**: over-engineering the process abstraction before real scanners exist to validate its shape — keep it minimal and let Phase 3 usage drive additions.

## Phase 3 — Windows Foundation

- **Objective**: First real scanners, on the platform the spec calls "first-class" (§302).
- **Scope**: `ServerSleuth.Windows` — OS scanner, Process scanner, Port scanner, Windows Service scanner, Installed Software scanner. Explicitly not IIS/COM yet (§1601-1603).
- **Projects**: `src/ServerSleuth.Windows/`, `test/ServerSleuth.Windows.Tests/`.
- **Models**: reuse Core entities (`OperatingSystem`, `Process`, `Port`, `Service`, `Software`); scanner-specific evidence sources per §7/§10/§12/§13.
- **Interfaces**: `WindowsServiceScanner`, `WindowsProcessScanner`, `WindowsPortScanner`, `WindowsSoftwareScanner`, `WindowsOsScanner` — each `IDiscoveryScanner`. Service scanner must not rely solely on `Get-Service`; must capture executable path, command line, service account, dependencies, recovery config via SCM/Registry/WMI as needed (§330-334).
- **Dependencies**: `System.Management` (WMI/CIM) if used; `Microsoft.Win32.Registry` for registry access. Guard all Windows-only package references so Core/Analysis/Reporting never reference them transitively.
- **Tests**: fixture-based where output can be captured (registry export snapshots, `sc query`/WMI sample payloads); live-environment smoke test kept separate/optional, not part of the default `dotnet test` run, since CI/dev machines vary.
- **Acceptance Criteria**: each scanner independently returns `DiscoveryResult` with entities + evidence + correct `ScannerStatus` on both a normal machine and a permission-restricted context (simulate via fixture, not requiring actual elevated/non-elevated dual test machines).
- **Risks**: WMI/registry access requiring elevation — must degrade to `AccessDenied` status, not crash the scan (§949-965).

## Phase 5 — Dependency Correlation

- **Objective**: Cross-entity correlation, kept out of scanners entirely (§1198-1219).
- **Scope**: `ServerSleuth.Analysis.Correlation` — rules: Process↔Service, Process↔Port, IIS↔AppPool, IIS↔Application, Application↔Runtime, Application↔DLL, Application↔COM, Application↔Configuration. Also deduplication/merge logic (§1180-1195).
- **Models**: consumes only Core entities + Evidence; produces `Dependency` edges into a `DependencyGraph`.
- **Tests**: each correlation rule tested in isolation with synthetic entity sets (no live scanner needed) — including a case producing no correlation (missing evidence) and a case producing conflicting evidence.
- **Acceptance Criteria**: correlation rules are named, independently unit-tested, and produce edges only when evidence supports them; duplicate entities from different scanners merge into one with unioned evidence, never producing two entities for the same logical component.

## Phase 6 — Linux

- **Objective**: Linux-native discovery, matching Windows scanner coverage.
- **Scope**: `ServerSleuth.Linux` — systemd, process, ports, packages (dpkg/apt, rpm/dnf, apk), runtimes, cron, Docker.
- **Models/Interfaces**: `SystemdScanner` (unit name, active/enabled state, ExecStart, user, env files, working dir, dependencies via `systemctl list-units`/`cat`/`show`), `PackageScanner` (normalized Package/Version/Architecture/Source/Status across all three package managers, not hard-coded to one distro per §719), `CronScanner` (crontab, `/etc/cron.*`, systemd timers), `DockerScanner` (containers/images/ports/volumes/networks/env var names only — never env values that look like secrets — entrypoint/command/restart policy/mounts).
- **Dependencies**: none beyond `IProcessRunner` from Phase 2 (shell out to `systemctl`, package manager CLIs, `docker inspect`).
- **Tests**: fixture-based against captured command output samples for each package manager and systemd states; Docker scanner tested against fixture JSON from `docker inspect` output, not a live daemon requirement in default test run.
- **Acceptance Criteria**: package scanner works when only one of the three package managers is present; Docker scanner degrades to `NotInstalled` when the Docker CLI/daemon is absent, not a failure.

**Status**: Phase 6A (Linux Foundation Discovery), Phase 6B (Linux Package/Runtime/Cron Discovery), Phase 6C (Linux Container Discovery), Phase 6D (Linux Kubernetes Discovery), Phase 6E (Linux Configuration Discovery), Phase 6F (Linux Native Dependency Discovery), and Phase 6G (Cross-Platform Integration & Real Linux Validation) are complete — see PROGRESS.md/CHANGELOG.md. Phase 6A covered OS/Process/Port/systemd-service discovery; Phase 6B added package discovery (dpkg/rpm/apk), runtime/SDK discovery (.NET/Java/Python/Node/npm/PHP/Go), and cron/scheduled-job discovery; Phase 6C added Docker and Podman container/image/volume/network discovery (`linux-container-scanner`), read-only only, with environment variable values never stored and no `Container → host Process` correlation performed; Phase 6D added Kubernetes cluster/namespace/node/pod/workload/service/ingress/ConfigMap/Secret(metadata-only)/PVC/PV discovery (`linux-kubernetes-scanner`) via read-only `kubectl` queries, with Secret values never retrieved or decoded and no `KubernetesPod`/`KubernetesContainer` → host correlation performed; Phase 6E added bounded configuration discovery (`linux-configuration-scanner`) across systemd/nginx/Apache/PHP/MySQL/PostgreSQL/Docker/SSH and already-discovered Service/ScheduledTask application roots, reusing the platform-neutral configuration-analysis architecture newly extracted to `ServerSleuth.Infrastructure.Configuration` (shared with Windows's `windows-configuration-scanner`); Risk Analysis, Migration Assessment, Reporting, GUI, and CLI production hardening remain unstarted, to be picked up in a later phase per the strict-stop condition Phase 6G was given.

## Phase 7 — Analysis

- **Objective**: Turn the dependency graph into risk, readiness, and unknown-dependency findings.
- **Scope**: `ServerSleuth.Analysis.Dependency`, `.Risk`, `.Migration` (Correlation already done in Phase 5).
- **Models/Interfaces**: `DependencyGraphBuilder` (assembles graph from correlated entities), `RiskRule`/`RiskEngine` (config-driven, Critical/High/Medium/Low categories from §864-901 — not hard-coded per-scanner branches, per §898-900), `MigrationReadinessCalculator` (explainable score per §1379-1404, every factor traceable), `UnknownDependencyDetector` (§1408-1433 — unknown port/process/service/DLL/COM/external endpoint, flagged rather than guessed), `MigrationChecklistGenerator` (§1349-1375, every item cites originating evidence).
- **Tests**: risk rule unit tests per category with synthetic graphs; readiness score tests verifying the breakdown sums/explains correctly; unknown-dependency tests confirming "preserve uncertainty" behavior (an entity with no correlating evidence is flagged Unknown, never guessed into a named component).
- **Acceptance Criteria**: no risk or score value is produced without an accompanying explanation object a report can render.

**Status**: Phase 7A (Evidence-Based Risk Engine) and Phase 7B (Risk Scoring & Risk Aggregation) are complete — see PROGRESS.md/CHANGELOG.md. `ServerSleuth.Analysis.Risk` implements a provider/rule-based `RiskRuleEngine` over twelve independently-testable `IRiskRule` implementations (RR1-RR12: MissingDependency, MissingBinary, AccessDenied, MissingRuntime, CertificateExpiry, ServiceDependency, ScheduledTaskDependency, ComDependency, ExternalDependency, SharedInfrastructure, ConfigurationRisk, GraphIntegrity), a deterministic `risk:{RuleId}:{SourceEntityId}:{normalized-related-ids}` finding identity scheme, a closed 12-category taxonomy, a Severity (Critical/High/Medium/Low/Info) that comes only from the rule that produced the finding — no 0-100 score anywhere in this phase — and a Confidence that never exceeds the confidence of its supporting evidence. `RiskAnalysisContext` is a pure, pre-indexed, read-only view over already-produced Discovery/Correlation/Boundary/Expansion/Validation artifacts: Risk Analysis never re-runs a scanner and never touches the filesystem/registry/process API/network/systemd/Docker/Kubernetes (confirmed both by `ServerSleuth.Analysis.csproj` referencing only `ServerSleuth.Core`, with no Windows/Linux/Infrastructure project reference or package reference of any kind, and by the engine/rules only ever reading `RiskAnalysisContext`'s in-memory indexes). `RiskRuleEngine` isolates rule failures (a throwing rule is recorded as a diagnostic and never aborts the run), enforces the non-Info-finding evidence invariant (dropping and diagnosing any that would violate it), deduplicates only via an explicit `MissingBinaryEntityId` merge anchor (preserving all contributing rule IDs and evidence, never silently discarding provenance), and sorts deterministically. Phase 7B added `ServerSleuth.Analysis.Risk.Aggregation` — `RiskAggregator`/`ApplicationRiskAggregator`/`ServerRiskAggregator`/`RiskSummaryCalculator` — transforming a `RiskAnalysisResult` into deterministic `ApplicationRiskSummary`/`ServerRiskSummary` aggregates with an `AggregateSeverity` (None/Info/Low/Medium/High/Critical) escalation policy (a single Critical finding always dominates, never averaged away), impact metrics (`AffectedEntityCount`/`AffectedBoundaryCount`/`SharedDependencyCount`), a max-not-average confidence aggregation, and a deterministic five-key Top-Risks ordering — still with no numeric score and no migration-readiness claim anywhere. Migration Readiness/`Migration` remain unstarted, to be picked up in a later phase (8) per the strict-stop condition Phase 7B was given. **Post-7B corrective task ("Shared Infrastructure Attribution Hardening", 2026-08-24)**: fixed a boundary-attribution bug flagged as a Phase 7B known limitation — a dependency shared by 3+ workloads (deliberately left as separate, un-merged boundaries per Phase 5B §8) was silently attributed to only whichever boundary a single-valued `Dictionary.TryAdd` happened to enumerate first. `RiskAnalysisContext` now exposes `BoundaryIdsByEntityId` (all claiming boundaries, ordinal-sorted, order-independent) and `RiskAggregator.ResolveAffectedBoundaryIds` attributes each finding to every boundary it actually affects (unioning `SourceEntityId` and `RelatedEntityIds` membership) while `ServerRiskSummary` still counts the logical finding exactly once. No Phase 5B or 7A code changed — see PROGRESS.md/CHANGELOG.md for the full root-cause trace and the 13 new tests that pin this down. **Phase 8A ("Migration Assessment Model & Policy", 2026-08-24)**: added `ServerSleuth.Analysis.Migration` — `MigrationAssessmentEngine` transforms Phase 7A/7B output (`RiskAnalysisResult`/`RiskAggregationResult`) into a `MigrationAssessmentSummary` via an explicit, RuleId-driven `MigrationPolicy` (never a blind `RiskSeverity → MigrationStatus` mapping — skill.md §1/§6). `MigrationStatus` is a 4-value classification (Ready/ReadyWithConditions/NeedsRemediation/Blocked, no numeric score) derived from each `MigrationIssue`'s `MigrationStatusImpact` (Informational/Unclassified/Conditional/RemediationRequired/Blocking), with the worst impact always winning outright. `MigrationDependency` represents external/shared dependencies separately from risk (a dependency can require verification without any RiskFinding backing it). Reuses `RiskAggregator.ResolveAffectedBoundaryIds` directly, so the Phase 7B shared-infrastructure fan-out automatically applies at the Migration layer too. No automatic remediation of any kind — assessment only. See PROGRESS.md/CHANGELOG.md for the full policy table, ERP fixture results, and the one real bug found+fixed during this phase (RR11-ConfigurationRisk's High-severity findings were being silently downgraded to Informational). **Phase 8B ("Migration Actions & Verification Planning", 2026-08-24)**: added `Migration/Actions` (`MigrationAction`/`MigrationActionType`/`MigrationActionPriority`/`MigrationActionPlanner`), `Migration/Verification` (`MigrationVerificationCheck`/`MigrationVerificationPlanner`), and `Migration/Planning` (`MigrationPlan`/`MigrationPlanEngine`), transforming Phase 8A's `MigrationAssessmentSummary` into a deterministic, evidence-backed, planning-only `MigrationPlan` — never executes anything (no file copy, no service/registry/IIS mutation, no shell/PowerShell/systemctl/docker/kubectl command of any kind). A RuleId-driven, closed mapping (mirroring `MigrationPolicy`'s own approach) turns each non-Informational `MigrationIssue` into exactly one `MigrationAction`; because Phase 7A's `MissingBinaryEntityId` merge anchor and Phase 8A's boundary fan-out already collapse cross-rule/cross-boundary duplicates upstream, one action per Issue is already "one logical action, many affected workloads" (verified with a shared-`host.exe`-across-3-boundaries fixture). Every action gets a matching Pre/Post `MigrationVerificationCheck`; every `MigrationDependency` with no matching action (no risk at all, or an Informational/Unclassified issue) still gets its own PostMigration check, never silently dropped. See PROGRESS.md/CHANGELOG.md for the full RuleId→ActionType table, ERP-plan fixture results, and performance numbers (10,000 issues/5,000 dependencies in ~88ms). **Phase 8C ("Server/Application Migration Assessment Consolidation", 2026-08-24)**: added `Migration/Consolidation` (`ServerMigrationAssessmentReport`/`ServerMigrationSummary`/`ApplicationMigrationSummary`/`MigrationDependencyGroup`/`AssessmentCoverage`/`CoverageWarning`/`ServerMigrationAssessmentReportEngine`), composing Phase 5B/5C/5D (`ApplicationBoundary`/`DependencyExpansionResult`/`GraphValidationResult`), 7B (`RiskAggregationResult`), 8A (`MigrationAssessmentSummary`), and 8B (`MigrationPlan`) into one final Server → Application → Dependency → Issue → Action → Verification view — deliberately NOT a second analysis engine (skill.md §2): every value in the output is copied verbatim from an already-produced upstream artifact, joined/filtered/grouped only. Introduces `AssessmentCoverage` (Unknown/Limited/Partial/Complete), derived solely from an optional `AggregateDiscoveryResult`'s scanner statuses and never allowed to influence `MigrationStatus` (skill.md §12 — verified explicitly: a `Ready` server can carry `Limited` coverage). Shared infrastructure and server-level issues are filtered views (never copies) over Phase 8A's own `Dependencies`/`Issues` lists; Phase 5D graph-validation errors pass through unmodified, with the existing Phase 8A RR12-GraphIntegrity policy remaining the sole Blocked/Ready authority. See PROGRESS.md/CHANGELOG.md for the full coverage policy, ERP-report fixture results, and performance numbers (10,000 entities/1,000 boundaries/10,000 issues/5,000 dependencies/10,000 actions/20,000 checks in ~97ms).

## Phase 8 — Reporting

- **Objective**: Render the assembled model to JSON (canonical/versioned), CSV, HTML.
- **Scope**: `ServerSleuth.Reporting.Json/Csv/Html`.
- **Models**: `schemaVersion`-carrying root JSON model per §1105-1139; HTML sections per §1071-1101 (Executive Summary through Migration Checklist); CSV as flat per-entity-type exports.
- **Tests**: JSON schema round-trip test (serialize known model → deserialize → equality); HTML report generation smoke test asserting each required section is present; CSV column presence tests. Snapshot/golden-file tests acceptable here given the intentionally fixed output shape.
- **Acceptance Criteria**: all three formats consume the *same* assembled model (no format computes its own derived numbers); HTML report is understandable without the original tool per §1101.

**Status**: Phase 9A ("Reporting Foundation & JSON Renderer", 2026-08-24) is complete — see PROGRESS.md/CHANGELOG.md. New projects `ServerSleuth.Reporting`/`ServerSleuth.Reporting.Tests` (one `ProjectReference`, `ServerSleuth.Analysis`; zero `PackageReference`s). `IReportRenderer`/`ReportFormat`/`ReportRenderResult` — a small, format-agnostic rendering abstraction; only `ReportFormat.Json` exists today. `JsonReportRenderer` serializes Phase 8C's `ServerMigrationAssessmentReport` (the "assembled model" this phase's own §125 acceptance criteria already anticipated) through a dedicated DTO tree (`Json/Dto/`) rather than the domain model directly — the DTO's fixed, explicitly-declared property list is the actual secret-safety/raw-configuration-safety boundary, on top of the redaction Phase 2/4E-1/6E already perform upstream. Deterministic (same input → byte-identical JSON, never dictionary/hash-set order dependent), UTF-8-safe with literal (non-escaped) Unicode via `JavaScriptEncoder.Create(UnicodeRanges.All)`, entirely in-memory (no `SaveToFile`/file export/HTTP/email/cloud upload — that belongs to a later composition/CLI layer). No `schemaVersion` field yet (deliberately deferred — not required by this phase's own scope, revisit once CSV/HTML renderers exist and a shared root-model versioning need is concrete); CSV/HTML remain unstarted, to be picked up in Phase 9B+ per this phase's own strict-stop condition. **Phase 9B ("Self-Contained HTML Migration Report", 2026-08-24)**: added `ReportFormat.Html`/`HtmlReportRenderer`/`HtmlDocumentStyles`/`CssClassName` under `Html/` — extends the same `IReportRenderer` abstraction and reuses Phase 9A's internal `ReportDtoMapper`, never a second reporting architecture. Produces a single, self-contained, fully-offline HTML document (inline CSS only, zero `<script>` tags — native `<details>`/`<summary>` handle collapse/expand with no JavaScript needed at all) via the same DTO-boundary secret-safety guarantee Phase 9A established. Every dynamic string passes through `HtmlEncoder.Create(UnicodeRanges.All)` (adversarially tested against script/attribute-injection payloads — none render live). Deterministic by default (`generatedAt` is opt-in, `null` unless a caller supplies it — no timestamp/GUID otherwise). Action grouping (Pre-Migration/Post-Migration/Review-Documentation) is derived purely from each action's existing `ActionType`/`Phase` fields, never inferred from free text. See PROGRESS.md/CHANGELOG.md for the full escaping/Unicode-encoder rationale, ERP-fixture results, and performance numbers (10,000-entity/1,000-application synthetic report rendered in ~384ms). PDF/CSV, GUI, CLI, and file-export composition remain unstarted, per this phase's own strict-stop condition. **Phase 9C ("Report Artifact & Local Export", 2026-08-24)**: added `Export/` (`ReportArtifact`/`ReportBundle`/`ReportArtifactFactory`/`ReportOverwritePolicy`/`ReportExportResult`/`ReportBundleExportResult`/`ReportManifest`/`IReportExporter`/`LocalFileReportExporter`) — the first Reporting component allowed to write to the filesystem, still using only BCL `System.IO` APIs against a caller-specified output directory (no Windows/Linux/Infrastructure reference added; `dotnet list reference`/`package` re-verified clean). Atomic write via same-directory temp-file + `Flush(flushToDisk: true)` + `File.Move(overwrite)` (OS-atomic replace/`rename(2)`); `FailIfExists` is the default overwrite policy everywhere. File names are always caller-independent (`report.json`/`report.html`, or a validated prefix) and additionally defense-in-depth-validated against path traversal/absolute-path/invalid-character injection via a platform-INDEPENDENT explicit blacklist (found during design that `Path.GetInvalidFileNameChars()`/`IsPathRooted` alone vary by host OS and would under-reject on Linux). `ReportBundle` guarantees JSON+HTML always originate from the same report instance — verified end-to-end with skill.md §10's own 6-step consistency scenario. An opt-in `report-manifest.json` (SHA-256 over the exact bytes written, safe metadata only, no timestamp unless explicitly supplied) is available but never generated by default. See PROGRESS.md/CHANGELOG.md for the full path-safety test matrix, ERP-fixture-exported-to-disk results, and render+export performance (~558ms at 10k-entity/1k-application scale). CLI/GUI/PDF/HTTP-API/email/cloud-upload/service-installation/self-update remain unstarted, per this phase's own strict-stop condition.

- **Scope**: `ServerSleuth.Cli` — argument parsing, DI wiring, `ScannerRegistry` population, profile-to-scanner-set mapping (§987-1035), orchestration of the full pipeline, output directory writing (§1519-1533).
- **Commands**: `scan [--profile quick|standard|deep|migration] [--output <dir>] [--format json,csv,html]`, `version`, `doctor`, `list-scanners`.
- **Dependencies**: a CLI parsing library (e.g. `System.CommandLine`) — decide and record in this file once selected; a DI container (`Microsoft.Extensions.DependencyInjection`) and a concrete logging provider (e.g. console) wired here, not in Core.
- **Tests**: CLI argument parsing tests, profile→scanner-set mapping tests, end-to-end smoke test running `scan --profile quick` against the current dev machine and asserting the output directory shape from §1519-1533 exists.
- **Acceptance Criteria**: `server-sleuth scan --profile migration --output ./migration-report --format html,json,csv` (§1062-1067) runs end to end and produces the fixed output directory; `list-scanners` reflects actual registered scanners with correct platform/profile metadata.

**Status**: Phase 10A ("CLI Foundation", 2026-08-24) is complete — see PROGRESS.md/CHANGELOG.md.
